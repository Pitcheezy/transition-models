# 협업 규약 v1 — 2026-10-12

> 각자 자기 레포에서 AI가 계속 일하고, 둘은 파일 계약과 이슈로만 만난다. 사람은 결정만 한다.

사용자가 2026-10-12 이 협업안을 전부 반영하도록 지시했다. 아래 역할과 작업 규칙은
우리 쪽 적용 기준이다. 과거 문서의 역할 미합의 문구보다 이 규칙이 우선한다.
역할 확정과 실제 파일 계약 검증·서비스 연결·공개 운영 완료는 구별한다.

## 1. 누구 것인가

- **Song:** 목표, 공개 발행 계약, 추천 모델, 발행기, 관전 화면.
- **우리:** 공개 호스팅, 업로드 받는 쪽, 이용 기록, 피드백, 감시·알림, 미트 자료.
- 상대 코드를 수정하지 않는다. 필요한 변경은 받는 레포의 `mail`로 요청한다.
  우리 AI가 상대 코드·프로세스·배포를 직접 다루지 않는 기존 제한은 유지한다.
- **만나는 곳은 공개 발행 파일(v1)과 업로드 API뿐이다.** 모델 가중치 이식이나
  상대 내부 API 직접 호출을 새 서비스의 선행 조건으로 만들지 않는다.
- 항목 추가는 알리고 진행한다. 항목 삭제·의미 변경은 **Song 승인 후 v2**로 올린다.
  AI는 변경안을 만들 수 있지만 계약 변경 결정과 대외 알림은 승인 범위 안에서 수행한다.
  알림 전 임의 변경이나 의미가 다른 값을 기존 필드로 보내는 것은 허용하지 않는다.
- 협업 규약 v1, 공개 파일 v1, 공개 발행 **문서 초안 v0**, IntentEstimate **v1.1**은
  서로 다른 버전이다. 우편 #18의 초안 v0 표기나 수신 스키마를 임의로 v1로 바꾸지 않는다.
  실제 연결에는 각각의 고정 소스·계약 버전·SHA를 기록한다.

## 2. AI가 하는 일과 사람이 정하는 일

- **AI 자율 범위:** 합의한 계약 안의 구현, 테스트, 문서, 조사, 검토, 로컬 리허설.
- **사람 결정:** 계약 변경, 우선순위, 접속 허용 대상, 비용이 드는 선택,
  실제 경기에 연결하는 일, 바깥으로 나가는 글.
- 사람이 이미 승인한 범위는 다시 묻지 않는다. 우편 수신만으로 권한을 확대하지 않는다.
- 결정이 필요한 항목은 `needs-human`과 우리 board의 `막힌 것 · 사람 결정 대기`에
  올리고, 이미 허용된 다음 독립 작업을 계속한다. 답이 없다고 완료 처리하지 않는다.
- 자기 board의 승인된 진행/증거 기록과 코드 PR은 기존 작업 절차로 유지한다.
  상대에게 보내는 회신·요청이나 새 대외 문구는 사람의 발신 승인 범위를 확인한다.
  범위가 없으면 로컬 회신 초안을 준비한다. 사람 결정 목록은 정기 회의 대신 사용한다.

  양쪽 열린 우편을 확인**하며, 착수 시에는 우리 선점 상태를 최신으로 다시 확인한다.
- 정기 회의는 두지 않는다. 사람끼리는 결정할 것만 이야기한다.

  예약 생성은 매일 실행 성공 증거가 아니다. 실제 실행/조회 실패는 기록하며 Song 쪽 확인 수행은 별도다.
  예약은 외부 발신·코드 수정·배포를 하지 않는다. 새 전달물/결정 필요/조회 실패 때만 알린다.
  로컬 예약은 기기와 앱이 켜져 있어야 한다([공식 안내](https://learn.chatgpt.com/docs/automations?surface=app)).
- 비밀은 사람이 직접 비공개 전달한다. 공개 이슈에는 비밀 값·서비스 접속 주소·IP/포트·터널·
  서명 URL·개인정보·개인 기기 절대 경로·비공개 영상/판독 원문을 쓰지 않는다.
  환경 변수 이름, 레포 상대 경로, 공개 코드/이슈 근거 링크는 사용할 수 있다.

## 4. 세션 규칙 세 줄

1. **시작:** 양쪽 board와 열린 mail의 본문·새 댓글, CHECKLIST, 실제 Git 상태를 확인한다.
2. **착수:** 일을 시작하기 전에 **이슈에 합격 기준**을 적는다. 관련 mail 또는 우리 board에
   무엇이 오면 끝인지 기록하고, 우리 board에 담당·AI·브랜치·기준 커밋·시각을 선점한다.
   CHECKLIST도 선점하며 다른 AI의 일을 중복 수행하지 않는다.
3. **종료:** 한 일·검사·커밋·산출물 SHA·다음을 같은 이슈에 남긴다. 실제 합격한 mail만 닫고,
   자기 board 진행 줄만 반납한다. CHECKLIST와 인계 문서는 작업과 같은 커밋에 갱신한다.

조회 예시(읽기 전용):

```sh
gh issue view 3 -R Pitcheezy/transition-models --comments
gh issue view 35 -R SongRoute/pitcheezy --comments
gh issue list -R Pitcheezy/transition-models -l mail --state open
gh issue list -R SongRoute/pitcheezy -l mail --state open
gh issue view <받은_번호> -R Pitcheezy/transition-models --comments
```

조회 실패를 우편 0건으로 기록하지 않는다. 선점을 확인할 수 없으면 공유 파일의 충돌 가능한
변경을 보류하고, 이미 맡은 안전한 로컬 작업을 계속한다. board 편집 직전 다시 읽고 편집 뒤
재조회한다. GitHub 본문은 원자적 잠금이 아니므로 CHECKLIST 한 도구 수정·선점 커밋을 유지한다.
시간이 지났다는 이유로 타인의 미커밋 변경·자료·서버를 덮어쓰거나 종료하지 않는다.
최신 main에서 짧은 브랜치/PR로 작업하며 기존 변경은 보존한다.

board는 다음 네 구역을 유지한다:

```text
## 지금 목표
## 진행 중 (담당 사람 / AI / 브랜치 / 시작 시각)
## 막힌 것 · 사람 결정 대기
## 최근 결정 (최근 5개, 날짜와 근거 링크)
```

## 5. 증거와 다른 모델의 검토

- 모든 산출물에는 **소스 커밋·실제 파일 SHA-256·실행 명령과 결과**를 붙인다.
  파일 없는 질의는 해시를 `해당 없음(파일 산출물 없음)`으로 쓴다.
- 재지 않은 수치는 **미측정**이다. **합성 자료 / 오프라인 재생 / 실경기** 결과를 분리한다.
  AI 검사와 독립 사람 검토, Windows WebKit과 실제 Safari, 로컬 복원과 클라우드 복원을 혼동하지 않는다.
- 실제 운영에 들어갈 코드는 **작성한 AI와 다른 모델**이 고정 커밋을 검토해야 한다.
  작성/검토 모델 식별자, 검토 커밋, 지적과 해결 여부, 재현 명령을 남긴다.
  같은 모델의 다른 세션/보조 에이전트는 추가 검토이지 이 조건 충족이 아니다.
  제품 이름만 다른 경우도 충분하지 않다. 실제 모델이 불명확하면 검토 조건 미충족이다.
- 기존 운영 후보의 별도 Codex 검토는 삭제하지 않되, 다른 모델이었다는 증거가 없으므로
  새 출시 조건 통과로 소급하지 않는다. **WS-review1**로 실제 운영 전 검토한다.
- SHA 일치는 파일 식별 근거이며 권리·출처 인증·모델 실행·사람 검토의 증거가 아니다.
- 우편 양식은 [.github/ISSUE_TEMPLATE/mail.yml](../.github/ISSUE_TEMPLATE/mail.yml)을 사용한다.

종료/회신 기록 형식:

```text
합격 기준 / 실제 완료 / 남은 조건:
산출물 상대 경로:
소스 전체 커밋 / 파일 SHA-256:
실행 명령 / 결과 / 미측정:
증거 종류: 합성 자료 | 오프라인 재생 | 실경기 | 해당 없음
작성 모델 / 검토 모델 / 검토 대상 커밋:
사람 결정 필요 / 다음 작업:
```

## 6. 월드시리즈 운영 규칙

- 대상 운영 기간은 **2026-10-23~31**. **10/21 이후에는 고장 수리만** 한다.
  일정 변경과 기능 추가 우선순위는 사람이 결정한다. 날짜 도달이 출시 승인은 아니다.
- **10/20까지 연락 수단과 각자의 응답 가능한 시간대**를 정한다. 연락처는 비공개 전달하고
  공개 이슈에는 결정 여부/담당만 기록한다.
- 문제가 보이면 **Song 또는 우리 담당 사람 누구든 즉시 공개 화면을 안내 문구로 바꿀 수 있다.**
  상대의 사전 응답을 기다리느라 내림을 지연하지 않는다. 내린 뒤 사유·시각·영향을 이슈에 기록한다.
  실제 조작 권한/경로는 미구현 스위치와 함께 준비하고, 미리 승인된 안내 문구를 사용한다.
  AI는 사람의 긴급 지시나 사전 위임 범위 안에서만 조작한다. 복구/다시 공개도 사람 결정 범위를 따른다.
- **발행 중단 알림은 둘 다 받는다.** 맥미니 원인은 Song, 호스팅 원인은 우리가 먼저 조사한다.
  분류가 안 되면 양쪽에 알리고 인계를 남긴다. 현재 단발 감시와 실제 알림 연결을 구별한다.
- **경기 종료마다 이용 기록 요약과 문제 목록을 이슈에 남긴다.** 경기 ID·집계 기간·동의/누락 범위·
  장애와 조치·커밋/해시/명령·미측정을 포함한다. 수집 OFF/자료 없음은 사용자 0명으로 바꾸지 않는다.
  11월 전시 근거로 보존하며 게시 문구/자동 게시 범위는 사람의 발신 승인을 따른다.
