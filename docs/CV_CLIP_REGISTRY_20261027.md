# CV47 — 투구별 공식 클립 등록부와 5경기 다운로드

## 왜 하는가

목표 흐름은 투구마다 ① 상황별로 투구 직전에 형의 추천 모델이 구종·위치를 추천하고 ② 포수 셋업이 그 위치와 얼마나 맞았는지(유도) ③ 투수가 셋업 위치에 던졌는지(제구) ④ 상황과 별개로 타자가 잘 친 것인지(결과)를 보는 것이다. ②의 미트 셋업 점은 우리 CV 몫이다. 지금까지 셋업 비교 표본은 2경기 58구뿐이라 ②~④를 나눠 볼 수 없었다. 이 단위는 투구별 공식 클립과 그 신원·결과를 한곳에 모아 표본을 경기 단위로 늘리는 토대다. 영상 내용 분석·정확도 주장은 이 단위 범위 밖이다.

사용자 승인(2026-10-27): 5경기 공식 자료 다운로드, 외장 SSD 보관. 형 추천 요청은 추후 결정. [착수 기록](https://github.com/Pitcheezy/transition-models/issues/3#issuecomment-6436146975). 작성 Claude Opus 5.5(`claude-opus-5-5`), 브랜치 `claude/clip-registry-1027`, 기준 main `4e6aba7`(CV 연구 PR 사슬과 독립).

## 등록부 구조 (`src/data/clip_registry.py`, 외장 SSD의 비공개 `<CLIP_ROOT>/registry.sqlite`)

- `games`: 날짜·시즌·경기 종류·팀·구장·분할, feed/Statcast/manifest SHA.
- `pitches`(투구 전 정보만): playId(기본키), 경기·타석·투구 번호(유일), 이닝, 투수·타자 ID·이름·좌우, 카운트·아웃·주자·점수.
- `outcomes`(투구 후 정보, 별도 테이블): 구종·구속·plate_x/z·zone·결과·타구 종류·타구 속도·발사각.
- `identity_issues`: 대조에 실패한 투구와 사유. 이 투구들은 `pitches`에 넣지 않는다.
- `clips`: 상태(pending/downloaded/no_media/ambiguous_media/failed)·시도 수·실패 사유, 페이지 스냅샷 경로·SHA, 관측된 mp4 후보, 파일 경로·SHA·크기, ffprobe로 읽은 길이·fps·time base·시작 시각·해상도·코덱.

신원은 기존 `build_game_manifest`로 검증한다. 경기·타석·투구 번호로 Statcast와 feed를 맞추고, 투수·타자·구종이 서로 맞아야 통과한다. 클립은 이렇게 확인된 playId로만 짝짓고, 목록 순서나 파일 순서로는 짝짓지 않는다.

## 받는 방식

- 경기 feed는 statsapi.mlb.com, Statcast는 baseballsavant.mlb.com에서 받는다. 747139는 기존 로컬 feed와 2024 parquet을 그대로 쓴다. 원본 바이트는 `sources/<game_pk>/`에 둔다.
- 클립은 Savant 공식 페이지(`sporty-videos?playId=`)에서 관측된 mp4만 받는다. URL을 추측하거나 스트림을 우회하지 않는다. 리다이렉트는 따라가기 전에 매 단계 HTTPS mlb.com인지 확인한다. 페이지 5MB·클립 80MB 상한을 둔다.
- 한 페이지에 서로 다른 mp4가 둘 이상이면 고르지 않고 `ambiguous_media`로 남긴다.
- 한 번에 한 요청씩 보내고 페이지 요청과 영상 요청 앞에 각각 1초를 쉰다(CLI는 1~60초만 허용). 경기 등록도 원본 요청 앞에 1초를 쉰다. 투구당 최대 2회까지 시도한다. 연속 8회 실패하거나 영상 없는 페이지가 연속 8회 나오면 멈춘다(차단·안내 화면도 영상이 없기 때문). 영상 없는 페이지는 `--retry-no-media`로만 다시 시도한다. 실패 사유와 받은 페이지 정보는 행마다 기록한다.
- 영상은 임시 이름으로 받아 ffprobe가 읽은 뒤에만 최종 이름을 준다. 깨진 영상이 재시도를 막지 않는다. ffprobe가 없으면 시작 전에 멈춘다. 중단(Ctrl-C)은 시도 수에 넣지 않는다.
- 기존 바이트는 덮어쓰지 않는다. 페이지는 방문할 때마다 바뀌므로(같은 투구가 10/6에는 88,229B, 오늘은 88,101B) 스냅샷 이름에 내용 SHA 앞 12자리를 붙여 서로 겹치지 않게 한다.
- 원본(feed·Statcast)은 경기 번호와 행 존재를 확인한 뒤에만 저장한다. 다시 등록할 때 manifest나 분할이 다르면 파일을 쓰기 전에 거부한다.
- 849843 첫 타석 3구는 10/6에 기록해 둔 공식 클립과 크기가 바이트 단위로 같았다(5,139,146 / 3,788,892 / 4,070,010).

## 결과

1,466구 전부 받았다. 실패·영상 없음·후보 둘 이상은 0건이다. 모든 투구가 첫 시도에 받혔고, 모든 페이지에 mp4 후보가 정확히 하나였다. 받은 시각은 2026-10-27 07:25~08:44 UTC(약 78분)다.

`status`는 기본으로 모든 파일을 다시 읽어 기록된 크기·SHA와 맞는지 확인한다. 아래 표는 그 확인을 통과한 수다([요약](results/clip_registry_20261027/summary_v1.json)).

### 다른 모델 검토

- 1차: Fable 5.1(`claude-fable-5-1`)이 `458993c`를 검토해 22건을 냈고 재현 검증에서 20건이 확인됐다. 전부 `1c70e76`에서 고쳤고 지적마다 회귀 검사를 더했다(검사 34개 통과).
- 2차: Fable 5.1이 `1c70e76`을 재검토했다. 1차 지적 20건 중 18건은 해결, 2건은 부분 해결이었다. 부분 해결 하나는 재시도에 성공하면 앞 시도의 페이지 스냅샷이 파일로만 남고 등록부는 마지막 시도만 가리킨다는 점이다. 의도한 동작으로 남긴다. 다른 하나는 한 경기의 원본 두 개가 함께 검사되지 않는다는 점이며 `c99166c`에서 고쳤다. 새 P3 후보 5건은 자동 검증 단계가 Fable 사용량 한도로 돌지 못해 작성 모델이 직접 재현 검사를 썼다. 다섯 건 모두 `c99166c`에서 고쳤고, 새 검사 6개는 `1c70e76`에서 실패하고 `c99166c`에서 통과한다(검사 39개 통과).
- 3차(2026-10-31): Fable 5.1이 `c99166c`를 검토했다. 다섯 건 모두 해결, 새 P3 1건(작은따옴표 JS 문자열 둘이 한 URL로 합쳐짐)은 `c405543`에서 되돌렸다.
- 4차: Fable 5.1이 `c405543`을 APPROVE했다. 저장된 1,466개 페이지 전부에서 등록부와 같은 영상 주소가 다시 나왔다. 백틱 문자열 병합은 기존부터 있던 P4로 실제 페이지에는 없다.

## 한계

- 클립의 카메라 시점(중견수 시점인지, 리플레이인지)과 set→릴리스 구간이 있는지는 아직 검사하지 않았다. 다음 단위에서 자동 검사하고 통과하지 못한 클립은 기권한다.
- 클립 안 시각과 릴리스 시각의 대응, 미트 위치, 정확도는 미측정이다. 정확도를 말하려면 클립 프레임 위에 사람이 찍은 기준 표시가 필요하다. 기존 사람 표시 84구는 다른 영상의 프레임이라 그대로 쓸 수 없다.
- MLB 영상은 저작물이다. 비공개로만 보관하고, Git·공개 이슈에는 메타데이터·SHA만 남긴다. 전시나 공개 화면에 쓸지는 사용자가 따로 정한다.
- 형 추천(사전 계산 JSON)은 아직 연결하지 않았다(사용자 추후 결정).
