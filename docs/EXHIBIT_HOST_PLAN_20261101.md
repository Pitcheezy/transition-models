## 왜 ZIP을 그대로 올리면 안 되나

형 앱은 페이지 기준 상대 주소 `./v1/...`로 자료를 읽는다. 우리 Worker는 `/v1/...`를 R2의 발행 기록에서만 읽고,
그 기록은 인증된 업로드 경로(`/_publish`)가 머리말을 붙여 저장한다. 그래서

- 화면 4개(index.html, favicon.svg, assets/*.js, assets/*.css) → Worker 정적 파일(ASSETS)
- 자료 24개(v1/*.json) → 업로드 API로 한 파일씩 등록(첫 생성 조건 `If-None-Match: *`)

으로 나눠야 한다. 형 파일은 한 바이트도 바꾸지 않는다.

## ④ 도메인 전환 — 선택지

**A안(권장): 서비스는 하위 도메인, 입구는 pitcheezy.com**

- `app.pitcheezy.com`(이름은 결정) → 우리 Worker. 형 앱이 주소 맨 앞(`/`)에서 그대로 돈다. gateway 수정 없음.
- `pitcheezy.com` → 홈 한 페이지(영상·소개·"서비스 열기" 버튼 → `app.pitcheezy.com/?game=849843`).
  - A1: 홈은 당분간 Sites에 두고, Codex 복귀(11/4 16:04) 뒤 홈 외 페이지를 내린다.
  - A2: 홈도 Cloudflare로 옮겨 Sites를 완전히 내린다(정적 홈 1개 추가 배포).
- 장점: 기존 QR(pitcheezy.com)이 그대로 유효하고, 되돌리기는 하위 도메인 연결만 해제하면 된다. 형 회신3의 "입구 한 페이지"와 맞는다.

**B안: pitcheezy.com 전체를 Worker로**

- QR을 찍으면 바로 형 앱. 홈 페이지를 같이 두려면 형 앱을 하위 경로(`/app/`)에 둬야 하는데,
  형 앱이 `./v1`을 상대 주소로 읽으므로 gateway에 `/app/v1` 경로 처리 추가가 필요하다(코드 변경·다른 모델 검토 추가).
- 되돌리기: 전환 전 DNS 레코드 값을 기록하고, Worker custom domain 해제 후 원래 레코드 복구. HTTPS 인증서 발급에 몇 분 걸릴 수 있다.

## 로컬 리허설 — 우리 gateway에 형 빌드 설치

③을 하기 전에 같은 구성을 이 노트북에서만 돌렸다. 우리 실제 Worker 코드(gateway·안내·접근 코드)를 loopback Miniflare로 띄우고,
정적 4개는 ASSETS로, 자료 24개는 실제 인증 업로드 경로로 넣었다. Cloudflare·실도메인·CDN은 쓰지 않았다.

| 확인 | 결과 |

| 자료 24개 업로드(첫 생성 조건) | 24/24 저장 |
| 공개 `/v1`에서 읽은 바이트 = 받은 원본 | 24/24 일치(저장 머리말 제거 확인) |
