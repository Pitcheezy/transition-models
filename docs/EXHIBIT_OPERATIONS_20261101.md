## 아침 시작 순서 (약 10분)

1. **호스트 확인(노트북 아무거나):** `app.pitcheezy.com/?game=849843`이 열리고 첫 투구가 보이는지. 운영자용 안내 상태 조회에서 OFF인지 확인하고, 화면이 정상 복원됐는지도 따로 확인한다. 추천 카드가 잠시 남아 있는 것만으로 OFF라고 판단하지 않는다(정기 재조회 전일 수 있음). 11/21 접근 코드 OFF는 목표 일정이며, 별도 공개 전환 승인과 적용 기록이 있는 경우에만 로그인 없이 열리는지 확인한다. 승인 전에는 접근 코드 ON을 유지한다.
2. **모니터 2:** 팩 폴더에서 터미널 열기 → `python -B verify.py`(Windows에서 `python`이 안 되면 `py -3 -B verify.py`) → "Verified 270 files" 확인 → `python -B serve.py` → 표시된 주소 `http://127.0.0.1:8741/?pitch=849843:1:1`를 Chrome에서 열기 → 전체 화면 버튼. 터미널 창은 최소화만 하고 닫지 않는다.
3. **모니터 1:** 형 쪽 절차. 첫 타석(1회 초 Pete Crow-Armstrong 1구)에 맞춘다.
4. **폰 1대로 QR 실제 스캔** → 홈 → 서비스 열기 → 경기 화면까지 열리는지.

## 문제가 생기면

| 증상 | 조치 |
|---|---|
| 모니터 2에 "serve.py 터미널이 켜져 있는지 확인" 메시지 | 터미널이 닫혔다. 같은 폴더에서 `python -B serve.py` 다시 실행 → 같은 주소(8741)면 열려 있던 탭에서 "이 공 다시 불러오기". 다른 포트로 열렸다고 나오면 터미널에 표시된 새 주소로 다시 연다. |
| 클립 하나만 오류 | "다음 공 →"으로 넘어가고 끝나고 기록. |
| 모니터 2 전체 화면에서 공 표시가 안 보임 | 플레이어의 "전체 화면" 버튼을 쓴다(영상 자체의 전체 화면 버튼은 공 정보를 가린다). |
| 관람객 폰에서 추천이 안 보이고 점검·확인 안내가 보임 | 운영자용 상태 조회와 현재 오류를 먼저 확인한다. 안내 ON이면 켠 담당자·사유를 확인하고 해결 뒤 OFF한다. 문구만 보고 일반 장애를 안내 ON으로 단정하거나 자동 해제하지 않는다. 새 후보 앱의 maintenance 문구는 "서비스 점검 중이에요. 잠시 후 다시 확인해 주세요."이며 실제 적용 버전은 CHECKLIST를 따른다. |
| 호스트 장애(자료 503, 화면 깨짐) | 운영자 토큰 보유자가 **안내 스위치 ON**(절차 ops/public-host/NOTICE.md, `notice-cli.mjs --plan … --execute`). 폰 화면은 추천을 숨기고 안내만 보여 준다. 원인 해결 뒤 OFF. 모니터 2는 로컬이라 계속 쓸 수 있다. 모니터 1도 Song의 로컬 재생 경로로 준비한 경우에만 호스트 장애와 분리된다. 공개 앱을 쓰는 경우에는 함께 영향을 받으므로 리허설에서 로컬 대체 경로를 확인한다. |
| 폰이 "접속 코드" 화면 | 승인된 공개 범위와 현재 적용 상태를 확인한다. 공개 전환 승인 전에는 접근 코드 ON을 유지하고 본인에게 전달된 코드로 확인한다. 화면이 나온다는 이유만으로 제한을 끄지 않는다. |
| 요청량 | Cloudflare 대시보드의 실제 요청 수를 점심·저녁에 확인한다. 기존 시간당 약 480요청은 폴링 횟수의 계산치이며 초기 접속·정적 파일·로그인·재시도 포함 범위를 검증하지 않았다. 30~50명 동시접속 수용량·전시 당일 총요청은 미측정이다. 현재 요금제/포함량과 실측 결과를 확인해 예산 변경을 사용자에게 제안하며 자동 전환하지 않는다. |
