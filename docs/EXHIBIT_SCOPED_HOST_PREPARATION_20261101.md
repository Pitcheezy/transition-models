## 승인 단계 3 — 자료6 최초 업로드

호스팅 담당 한 명만 새 시험 서버에 발행한다. 6종류 키를 넣으므로 기존 한 키 시험의 scope를 재사용하지 않는다. 새 서버에만 최대10분의 수동 업로드 창을 열고 `PUBLISH_KEY_SCOPE`·`PUBLISH_EXPIRES_AT` 두 변수를 모두 두지 않는 legacy 발행 모드다. 이 토큰은 같은 서버의 다른 허용 v1 키에도 쓸 수 있고 서버 자동 만료도 없다. 이 범위까지 사용자에게 설명하고 별도 승인받은 뒤에만 실행한다. 업로드 종료·오류·창 종료 시 운영자가 OFF와 digest 교체를 책임진다. 실행기의 시각 제한은 추가 요청을 멈출 뿐 서버 권한을 자동으로 끄지 않는다.

### 실행 전 고정할 것

- 형 자료6개·739955bytes는 [원본 SHA 목록](results/exhibition_20261101/scoped-host-preparation.json) 그대로다. 순서는 setup → game → games → dates → manifest → health. 수신 원본·기존 앱·다른 경기 파일을 수정하거나 삭제하지 않는다.
- [일회 실행기](../ops/public-host/exhibit-stage3-upload.mjs)의 기본 동작은 dry-run이다. 기존 publisher-cli의 기본3회 재시도는 이번 원장에 사용하지 않는다. 실행기는 12계획/원본바이트/전송대상/최초생성 조건을 전부 먼저 검사하고, `maxAttempts:1`·요청당5초 제한으로 송신한다.
- 비공개 준비 manifest는 `approved:false`, 시작/종료시각 null이다. 승인 뒤 새 실행 사본에 UTC 창, run_id, 관리 조회로 확인한 최종 적용 버전, 정확한 서버·12계획SHA를 고정하고 manifest 전체SHA를 다시 기록한다. 토큰 등록·ON 설정으로 바뀐 버전을 이전 준비 버전과 혼동하지 않는다.
- 임시 발행 토큰은 승인 후에만 생성한다. 토큰은 Git 밖 사용자 전용 ACL 파일에만 두며 exFAT 자료 폴더·명령 인자·화면·로그에 쓰지 않는다. 2026-11-02 후속 사용자 지시로 임시 발행 비밀 등록·종료교체는 Codex가 수행하며 [실행 기록](EXHIBIT_STAGE3_EXECUTION_20261102.md)에 결과를 모은다. [단일 발행 비밀 등록 도우미](../scripts/register_exhibit_stage3_publisher.py)의 명시 실행은 교차검토 뒤 진행한다. 기존 `--register` 사용자 직접 방식은 선택 사항이며 기본 dry-run·고정 입력·단일 PUT 제한은 유지한다. `initial`은 정확한 기존비밀3→4, `rotate`는4→4이며 두 단계 모두 관리 버전·실제 전체vars/OFF를 전후 대조한다. 고정 Wrangler4.151.0의 stdin으로 PUBLISH_TOKEN_SHA256 한 개만 등록하고 버전을 기록한다. [가드](../scripts/exhibit_stage3_cli_guard.cjs)는 고정계정/Worker/명령/64hex PUBLISH본문의 PUT1회만 허용한다. manifest/설정/Node/CLI의 공식bin·dist 두 실행파일/가드SHA를 검증하며 기본은 로컬 dry-run이다. 이미 시작한 출력 폴더나 불명확한 pending은 재실행하지 않는다. 기존 단계2의 비밀3개 등록 도우미는 재사용하지 않는다.
- 단계2 OFF 설정SHA `a7c4464ed07c29830a508b612c45baf00eb9faf60e4806d76fc50d35c5097b77` 원본은 보존한다. 승인 후 새 사본에서 UPLOAD_ENABLED만 true로 바꾸고 설정 검사·바인딩 대조를 통과한 경우에만 적용한다. 종료용 OFF 사본도 같은 자원/코드/현재 비밀을 유지하는지 먼저 확인한다. storage-stage1 합성 카운터 사본 또는 비밀 등록 전 버전으로 복귀하지 않는다.
- 새 출력 폴더는 한 번만 만든다. started·요청별 pending/completed를 전송 전후 디스크에 저장하며 기존 출력 폴더를 거부한다. 실패 후 폴더 이름을 바꿔 다시 실행하거나 부분자료를 덮어쓰지 않는다. 실제 서비스 원장은 비공개 보관하고 공유 기록에는 자원명·주소·Ray·쿠키·토큰을 제외한다.

### 유한 원장과 종료 순서

1. 관리 조회로 새 시험 대상·비밀4개 이름·로그100%저장·현재 vars/bindings를 대조한다. 접근 코드·자료 읽기 ON, 수집/피드백 OFF를 유지한다. 승인된 창에서 업로드만 ON으로 적용하고 새 버전을 고정한다.
2. **서비스 요청1~6: HEAD6.** 모두404/missing이어야 PUT으로 진행한다. 기존 파일200·401·403·429·503·시간초과·통신 불명확 중 하나라도 나오면 중단하고 4번으로 간다.
3. **서비스 요청7~12: PUT6.** 각 `If-None-Match:*`, 응답200/stored 및 반환 원본SHA 일치가 필요하다. 각 요청은1회뿐이며 자동 이동/재시도는0이다. 전체 자료를 R2에 직접 복사하지 않는다. 요청별 UTC 시작/종료·응답status·가능한CF-Ray·관리 고정 버전 근거를 비공개 원장에 기록한다. 버전 고정값은 서버 로그로 확인한 버전과 구분한다.
4. 성공·실패 모두 **업로드 OFF 적용을 먼저** 하고 적용 버전/설정을 관리 조회로 확인한다. **서비스 요청13: 자격 없는 HEAD /_publish/v1/health.json 1회, 503 예상**. 오류/요청 불명확이어도 자동 재시도 없이 기록한다. 앞에서 멈췄다면 총요청은13 미만이다.
5. 임시 발행 digest를 새 무작위 값에서 얻은 digest로 교체해 기존 토큰을 무효화하고, 최종 버전·비밀 이름·OFF/로그/접근 설정을 관리 조회로 확인한다. 2026-11-02 후속 승인대로 Codex가 교체하고 위 실행 기록에 결과를 모은다. 확인 뒤 환경변수와 임시 토큰 원문 파일만 폐기한다. 받은 자료·요청원장·자원은 보존한다. 이 순서에서 옛 토큰401은 실측하지 않는다(OFF 상태가 먼저503을 반환함).

정상 서비스 요청 상한은 **12+종료확인1=13회**, 관리 조회·설정 변경·비밀 등록은 별도 운영 원장으로 센다. 실행기는 남은 요청시간에30초를 더한 여유를 검사하지만 이것이 종료 설정 반영시간의 보장은 아니다. OFF/회수 실패는 즉시 사용자에게 알리고 새 요청을 보내지 않는다. 이미 승인된 비상 분리 절차가 필요하면 사용자가 새 시험 Route/DNS만 해제하고 자원은 보존한다.

## 승인 단계 5 — 공개 앱 연결 교체

### 착수 조건과 변경 범위

이 절은 전환 계획이며 실제 승인·적용 근거가 아니다. [단계4 실제 자동 결과](EXHIBIT_STAGE4_RESULT_20261102.md)와 실제 폰 응답, 단계3·4 저장 서버 로그 대조를 먼저 모은다. 미확인·누락이 있으면 전환 HOLD로 남기고 자동 합격 처리하지 않는다. 최신 상태는 CHECKLIST만 갱신한다.

승인 전에 비공개 전환 원장에 기존 `app.pitcheezy.com/*` Route 하나의 식별자·기존 대상과 새 대상, 양쪽의 현재 적용 버전·접근/안내/업로드/로그 설정, 고정 후보10파일과 보조1파일 SHA를 기록한다. 이 조회는 앞으로 수행할 사전 확인이며 11/2 단계4의 관리 조회로 대체하지 않는다. 이름·계정·시험 주소·자격은 공개 기록에서 제외한다. 같은 주소의 중복 Route 또는 예상과 다른 대상이 있으면 멈춘다.

사용자에게 설명할 변경은 **기존 app Route 한 개의 대상만 새 Worker로 교체**하는 것이다. DNS/AAAA·Custom Domain·배포 버전·비밀값·홈/apex/www/media·옛 시험 Route는 바꾸지 않는다. 호스트 와일드카드나 설정파일 routes를 추가하지 않는다. 새 앱은 접근 코드 ON·자료 읽기 ON·업로드/수집/피드백 OFF·안내 OFF·로그 저장을 유지한다. 접근 코드 OFF·유료 전환은 별도 결정이다.

### 세션과 실제 사용 화면

시험 주소의 쿠키는 app으로 옮겨지지 않는다. 같은 접속 코드라도 새 Worker의 세션 서명키가 달라 기존 app 로그인은 다시 해야 한다. `access.mjs`의 HTTPS 쿠키는 `__Host-`·Path=/·Secure·HttpOnly·SameSite=Strict이고 Domain이 없는 호스트 한정 쿠키다. 쿠키를 복사하거나 새 인증값을 만들지 않는다.

이미 열린 앱은 옛 HTML/JS를 계속 표시할 수 있다. 실제 전환 뒤 폰 검사는 기존 탭 새로고침→필요 시 재로그인→849843의 추천·존·투구 이동, 새 비공개 탭→접속 코드→같은 경기 진입을 구분해 기록한다. 전환 전 별도 시험 주소에서 한 폰 검사와도 구별한다. 기본 절차에 계정 전체 캐시 삭제를 넣지 않는다. 로그아웃204는 해당 응답의 쿠키 삭제이며 모든 복제 세션의 서버 회수 증거가 아니다.

### 전환 후 유한 확인 계획

정상 확인은 `exhibit-stage4-read.mjs`의 `runStage4Read`만 재사용하는 **최대24요청(일반23+로그아웃 예약1)** 안이다. 자격 없는3주소401·업로드OFF503 → 로그인 → 형 정적4/자료6의 원본바이트와 헤더·지정 경기 진입·지정 제외주소404·보조 설정 → 로그아웃 순서이며, 오류면 일반검사를 멈추고 이미 발급된 세션의 로그아웃만 시도한다. 자동 재시도는 없다. 제외 잠금 경기의 응답 본문은 읽지 않는다.

기존 `run-exhibit-stage4.mjs`는 공개 app 주소를 의도적으로 거부하고 10분 관찰·안내 ON/OFF까지 묶으므로 **origin만 바꾸거나 보호를 해제해 실행하지 않는다.** 별도 `run-exhibit-stage5.mjs`가 위 읽기 함수만 재사용한다. 고정 구현 `7ec2e69733cfc651435a3ca10aeabf4a794e7475`의 [로컬 준비 영수증](results/exhibition_20261101/stage5-confirmation-preparation.json)에 모의 검사39통과·다른 모델 검토APPROVE·실제 원본의 dry-run을 기록했다. 도구 준비를 전환 승인으로 취급하지 않는다. 실제 진행 상태는 CHECKLIST에서 확인한다.

비공개 준비 입력은 approved=false·UTC창=null·버전=영(0) 자리표시자다. 실제 승인 뒤 새로운 입력 사본에서 `approved:true`, 정확한 양쪽 관리 버전, 최대15분 UTC 실행 창, 새 run_id를 고정하고 입력 원본SHA를 다시 계산한다. 준비본을 그대로 실행할 수 없다. 복구 입력은 실제 사용한 전환 입력SHA·전환버전에 다시 연결해야 한다. 명령 인자에는 코드·쿠키를 쓰지 않고 실행 단계에서만 보관 중인 코드 파일을 읽는다.

전환은 새 회차 폴더를 한 번만 만든다. 복구는 같은 회차의 전환 입력·버전 및 완료 영수증에 연결된 별도 한 번이며, 종료 영수증이 없는 실행 중/중단 회차를 자동 재실행하지 않는다. 종료 영수증은 있으나 HTTP 응답이 불명확한 실패는 그대로 남긴다. 이 경우에도 별도 승인과 수동 Route 복구 뒤 옛 앱을 확인할 수 있으며, 실패한 전환 요청을 다시 보내는 것은 아니다. 실행 도구는 Route나 자원을 바꾸지 않는다. 승인 창이 닫히면 일반 송신을 멈추고 이미 로그인한 경우의 로그아웃만 예약 한도 안에서 정리한다. 원격 응답·실패를 원장에 남기며 폴더를 바꿔 반복해 합격을 만들지 않는다.

24요청은 새 원본 바이트 확인이며 기존 열린 탭의 갱신·실제 폰·HTTP→HTTPS·안내 전환·동시접속까지의 검사가 아니다. 폰 조작과 관리 읽기는 서비스 자동24요청과 분리해 계획·기록한다. 각 요청의 Ray·시각·status와 관리에서 고정한 예상 버전을 보존한 뒤 저장 서버 로그의 실제 버전을 대조한다. 관리 버전 핀만으로 그 Worker가 각 요청을 처리했다고 쓰지 않는다. 안내 시험과 폴링 측정을 다시 실행하지 않는다.

### 실패 시 복구와 합격 판정

전환 또는 확인이 실패하면 준비한 기존 Route 대상을 그대로 복구한다. 옛 Worker의 **현재 자격이 등록된 버전**을 사용하며 비밀 등록 전 코드로 롤백하지 않는다. 두 Worker·R2·D1·기존 자료·시험 주소는 보존한다. 복구 후 기존 앱의 옛 날짜/경기 목록도 돌아오므로, 좁힌 새 전시 범위가 유지된다고 주장하지 않는다. 이 임시 복구 범위까지 전환 승인 전에 설명한다.

복구 확인은 새 c47 바이트 검사와 분리한다. 기존 서버의 고정 HTML/manifest를 사전 확인해 **최대5요청: 무자격GET / 401 → 로그인 → 옛 HTML 바이트 → 옛 manifest 바이트 → 로그아웃**의 별도 원장을 준비한다. 실패 시 일반 요청 중단·로그아웃 예약은 같은 원칙이다. 정상24+필요 시 복구5, 합계 최대29 서비스 요청 안으로 설명하며 실제 사용량은 따로 기록한다. 위 단계5 도구의 복구 모드와 별도 옛 기준 입력을 사용한다. 다른 빌드 바이트를 기대하는 새 후보 검사기를 옛 앱에 재실행하지 않는다. 복구 확인 합격도 옛 경기 전체 내용·실제 브라우저 동선·서버 로그까지 재검증한 뜻은 아니다.

새 app 쿠키로 바뀐 브라우저는 옛 서버로 되돌린 뒤 다시 코드 입력이 필요할 수 있다. Route 반영 시간은 미측정이며 무한 조회·재시도로 성공을 만들지 않는다. 복구도 불확실하면 결과를 사용자에게 알리고 추가 변경을 멈춘다. 실제 적용·HTTP·폰·서버로그 근거가 갖춰진 뒤에만 CHECKLIST 공개 버전 줄과 최종 회신에 전환 완료를 기록한다.
