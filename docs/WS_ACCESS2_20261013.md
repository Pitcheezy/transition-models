## 1. WS-access2 — 세션 길이 축소 뒤 쿠키 부활

**재현(main `9c99a5d`):** 2시간 설정으로 로그인한 쿠키를 설정 30분 축소 뒤 같은 쿠키로 판정했다.

| 로그인 후 | 판정 |
|---|---|
| 10분 · 60분 · 89분 | 거부 |
| 90분 · 91분 · 95분 · 119분 | **다시 유효**(90분은 남은 수명 = 설정이라 통과) |
| 121분 | 거부(원래 만료) |

원인은 "남은 수명 > 현재 설정이면 거부" 규칙이었다. 남은 수명은 시간이 지나며 줄어들어 결국 설정보다 작아진다.

**수정:** 쿠키 v2에 발급 시각을 넣고 함께 서명한다. 유효 조건은 서명 일치, 코드 digest가 목록에 있음, 현재 < 만료,
**(만료 − 발급) ≤ 현재 설정**, 발급 ≤ 현재 + 60초다. 수명·만료·코드·서명에 의한 거부는 설정이 같으면 이후 모든 시각에 유지된다(수명 규칙이 현재 시각과 무관).
시간에 따라 바뀌는 조건은 엣지 시계차 60초 경계 하나뿐이다.
설정을 늘리면 기존 세션은 원래 만료까지 유지된다. v1 쿠키는 발급 시각이 없어 받지 않는다(다시 로그인; 실제 배포 전이라 영향 없음).

**한계:** 설정을 원래 값으로 되돌리면 그 값으로 발급되고 아직 만료되지 않은 세션은 다시 유효하다(무상태 설계; 코드 삭제 후 재추가와 같다).
되돌려도 끝나야 하면 `ACCESS_SESSION_SECRET`을 회전한다. ACCESS.md에 적었다.

**검사:** 축소 후 0~180분 1분 격자 전부 거부, 축소 후 새로 받은 쿠키는 정상 만료, 연장 시 원래 만료 유지, 같은 길이 허용·1초 짧으면 거부,
정상 서명된 v1·수명 초과·만료≤발급·시계차 초과 발급·목록 밖 코드 거부. 실제 로컬 Worker: 6초 쿠키 발급 → 3초 설정으로 재시작 → 즉시 401,
발급 약 3.8초 뒤(남은 수명이 새 설정보다 작아진 구간, main이 다시 받아들이던 때) 다시 401, 새 쿠키 200. 이 런타임 검사는 main의 수명 규칙을 되살린
변형에서 실패함을 확인했다.

## 2. WS-access3 — 접근 문 × 수집 충돌

**재현(main `9c99a5d`, 실제 로컬):** 로컬 https Worker(Miniflare, 실행마다 자체 서명), 실제 로컬 D1(`migrations/0001_telemetry.sql`), Chromium.
접속 코드 로그인 뒤 쿠키는 `__Host-pz_viewer`(Secure·HttpOnly·SameSite=Strict)였다. 위젯에서 동의·의견을 누르자 `/_telemetry/session`·`/_telemetry/feedback`
모두 **쿠키 없이 401**(`X-Pitcheezy-Access: required`)이었고 D1은 0행, 위젯은 "통계 연결이 지연됩니다"로 오표시했다. usage-client가 항상 `credentials:"omit"`이었기 때문이다.

**수정:**
- 공개 수집 설정에 명시적 `accessGate`(기본 false)를 둔다. 설정 검사가 `ACCESS_GATE_ENABLED`와의 일치를 강제한다(불일치·타입 강제 변환·누락 거부).
- `accessGate:true`일 때만 `credentials:"same-origin"`(같은 출처 쿠키만)으로 보내고, false면 예전처럼 `omit`이다.
- 401 + 접근 헤더는 게이트가 수집 전에 그 요청을 거절한 것이므로 그 요청은 저장되지 않았음이 확실하다. 통계는 `access_required`로 참여를 끝낸다
  (동의 해제·체크 해제, 재시도·실패 누적 없음, 경기·UTC 날짜 변경으로도 재개하지 않음, 다시 접속한 뒤 새 선택으로만 새 세션).
  의견은 첫 시도가 거절되면 미저장 확정(다른 평가 선택 가능), 앞선 시도가 불확실했으면 같은 평가·같은 id로만 재시도한다. 헤더 없는 401은 예전처럼 일반 실패다.
- 위젯은 접근 문이 켜진 경우에만 "이 사이트의 쿠키(접속 확인용 포함)가 함께 전송되지만 기록에 저장하지 않는다"는 개발용 안내를 덧붙인다.
- 게이트 우회·수집 경로 예외·동의 완화는 하지 않았다. 수집 처리는 쿠키를 읽거나 저장하지 않는다.

**실제 로컬 조합 검사**(`tests/browser/host-access-collection.test.cjs`, 엣지의 `CF-Connecting-IP`는 로컬 엣지 대역 Worker가 설정):

| 경우 | 결과 |
|---|---|
| 세션 없음·가짜 쿠키 직접 전송(통계·의견) | 401·접근 헤더, D1·일일 예산 변화 0 |
| 로그인·미동의 60초 | 수집 요청 0 |
| 로그인·미동의 의견 | 200·쿠키 동반·저장 1 |
| 동의 | 200·쿠키 동반·세션 저장, 실제 2초 경과 뒤 갱신(sequence 1, 2,000 ms) |
| 철회 | 이후 요청 0 |
| 로그아웃 후 통계·의견 | 401·`access_required` 표시·체크 해제·미저장, 페이지 시계 25분 경과에도 재시도 없음 |
| 재로그인 | 동의 미승계(체크 해제), 재동의 시 새 세션 |
| 4초 세션 만료 | 만료 뒤 401·`access_required`·체크 해제·미저장, 이후 경기 변경에도 재개 없음 |
| 게이트 OFF·`accessGate:false` | 다른 쿠키 미전송(Chromium), 저장 정상 |
| 설정 불일치(게이트 ON·`accessGate:false`) | 401을 `access_required`로 표시·미저장(설정 검사가 이 조합을 거부) |

서버는 활성 시간을 세션 시작 후 실제 경과 시간 + 1초까지만 받는다. 페이지 가짜 시계로 30초를 주장하면 409였다. 그래서 저장되는 갱신은 실제 시간을 흘려 검사했다.
WebKit은 이 기기에 설치돼 있지 않다(내려받기는 사람 승인 필요). CI의 WebKit 작업이 같은 검사를 돌리고, WebKit이 `omit`에도 쿠키를 보내는 기존 현상은 진단으로 남긴다.

## 3. WS-monitor2 — 접근 문 ON 발행 감시

**이전:** 감시는 세션이 없어 게이트 ON이면 `page_access_required`·`health_access_required`만 남기고 발행 시각을 보지 못했다.

**보완:** 감시 설정 선택 키 `access_code_env`에 환경 변수 **이름**을 적으면, 매 실행 그 코드로 관람자와 같은 `POST /_access/v1/session`에서 세션을 받고
page/health를 그 쿠키로 읽는다. 우회 경로나 새 자격 증명 종류는 없다. 감시 전용 코드를 목록에 따로 두면 그 코드만 지워 감시 세션을 철회할 수 있다.
로그인 실패는 `access_login_*` 하나(page/health는 `skipped`), 세션 거부는 `*_access_session_rejected`, 로그인 경로 404인데 읽기가 막히면
`*_access_gate_without_login`이며 모두 알림 `host_error`(우리 우선)다. `access_gate_active`는 게이트 자체의 응답을 본 경우만 true다.
키가 없으면 예전 동작 그대로다. 코드와 쿠키는 report·state·stdout·stderr에 남지 않는다.

**검사:** 단위 9(설정 검증, 요청 전 코드 검사, 로그인→쿠키 동반 읽기, 게이트 OFF 404, 실패 코드 8종·읽기 생략·분류, 세션 거부, 404 뒤 게이트 읽기,
게이트 관측 표시, 쿠키 이름) + 실제 로컬 Worker 1
(게이트 ON 신선 → available; 코드 없음 → access_required; 틀린 코드 → access_login_denied; 오래된 health 2회 → incident open → 모의 알림 `publish_stalled`
Song 우선 양쪽; 복구 2회 → recovered; 안내 ON에서도 세션을 유지한 채 `notice_active`) + CLI 1(환경 변수 없으면 요청 없이 종료 2·상태 미작성, 있으면 available,
출력·상태에 코드·쿠키 없음). [리허설 영수증](results/ops/ws_monitor_gate_rehearsal_20261013.json).

## 4-1. 함께 고친 것 — 경기별 기록의 감시 범위 (WS-report1 결함, main에도 있음)

검토에서 확인됐다: 경기별 기록 초안은 감시 상태가 주어지기만 하면, 감시가 기간 중 관측하지 않았어도 "감시 이벤트 없음"으로 썼다.
WS-monitor2에서 감시 코드 환경 변수가 빠지면 감시가 요청 없이 종료 2로 멈추므로 이 오기가 생길 경로가 늘었다. 이제 상태의 `last_observed_ms`로
`monitor_coverage`(`covers_end`·`stopped_in_window`·`before_window`·`never`·`unknown`)를 판정해, 기간 끝까지 관측했을 때만 "이벤트 없음"으로 쓰고 나머지는
미측정 범위를 적는다. 리허설 입력도 `last_observed_ms`를 넘기도록 고쳤다.
