# WS-alert2 — 열린 장애의 원인 재분류 알림 (2026-10-13)

작성 모델 Claude Opus 5.5(`claude-opus-5-5`), 브랜치 `claude/ws-alert2`, 기준 main `28449cb5a805af142e873dd8208f79d691e1a09f`, 선점 `f0a2311`.
선점·합격 기준: [board #3 댓글](https://github.com/Pitcheezy/transition-models/issues/3#issuecomment-6142651700). **Codex 교차 검토 대상**(WS-review2)이며
이 세션의 검토는 같은 모델 계열 자체검사다. 실제 채널·연락처·발송은 없다(모의 transport).

## 문제 (main에도 같음)

감시는 장애를 연 두 번째 실패 실행의 issues로 범주를 고정한다(MONITORING.md: "열린 장애의 원인이 바뀌어도 opened를 반복하지 않는다").
알림도 그 범주만 썼다. WS-access2 자체 검토(`wf_1eb72b5a-240`)가 실제 상태 기계로 두 경우를 재현했다.

- 안내 화면 ON 중 열린 장애(정보, "조치 불필요")가 안내 OFF 뒤 발행 중단으로 이어져도 Song에게 `publish_stalled`가 가지 않았고 재알림도 "조치 불필요"였다.
- 감시 로그인 일시 실패(우리 우선)로 열린 장애는 이후 발행 중단이 되어도 우리 우선으로 남았다.

## 수정 (첫 검토 뒤 재설계한 판)

- 알림 CLI가 감시 상태 파일의 최신 `report`를 함께 읽는다. 상태에 마지막으로 기록된 실행(`observed_at_ms = last_observed_ms`)일 때만, 실행마다 한 번만 센다.
- **두 번 연속 규칙:** 감시가 장애를 여는 기준과 같이 새 범주가 기록된 실행 두 번 연속 나와야 원인을 바꾼다. 한 번짜리 일시 오류는 경로를 바꾸지 않는다.
- **알린 범주 기억(상태 v2 `incidents`):** 양쪽에 마지막으로 알린 범주를 장애별로 기억한다. 새 범주가 조치 필요(`publish_stalled`·`host_error`·`unclassified`)이고
  알린 범주와 다르면 양쪽에 번호 붙은 재분류 알림(`reclassified:<번호>:<범주>`, `event_kind:"reclassified"`)을 보낸다. 예전 원인으로 되돌아가는 것도 새 번호로 알린다.
- **정보성에서 올리기:** 알린 범주가 정보성인데 두 번 연속 조치가 필요하면 원인이 번갈아도 올린다(다르면 `unclassified` 양쪽).
- **낮추지 않음:** 정보성 범주(안내·접근 문)는 알린 범주를 대신하지 않고, 재알림은 마지막으로 알린 범주를 쓴다.
- **대체:** 새 재분류는 아직 전달되지 않은 이전 재분류를 모든 수신자에 대해 `abandoned`로 정리한다(늦은 재시도가 옛 원인을 남기지 않음). 메시지에 `announcement` 번호.
- **정리 규칙 결함 함께 고침:** WS-review1에서 더한 30일 정리가 감시가 아직 목록에 둔 opened/recovered 행까지 지워 그 알림을 다시 보내던 결함을 고쳤다.
- **재시도·정리:** 재분류 알림은 저장된 대기열에서 현재 원인과 무관하게 재시도한다. 장애가 닫히면 미전달 재분류·재알림(지난 재알림 창 포함)은 `abandoned`로
  정리되고 보관 기간 뒤 지워진다.
- **순서:** 수신자의 opened 알림이 재시도 중이면 그 수신자에게 재분류·재알림을 미룬다.
- **형식 오류:** 틀린 감시 이벤트·장애는 건너뛰고 나머지를 보낸다(receipt 표시, 종료 1).
- 메시지 v2는 `cause_observed_at`·`reclassified_from`을 더한다. 경기별 기록은 상태 v1·v2를 받고 `abandoned` 수를 따로 센다.
- 감시 상태 기계·이벤트 형식은 그대로다. **되돌리기:** 이전 코드는 v2 상태를 거부한다. `alerts-cli.mjs --downgrade-to-v1 <새 파일>`이 중복 방지 기록을 유지한
  v1 사본을 만든다. 빈 상태로 시작하면 감시가 목록에 둔 opened/recovered 이벤트(최대 100건)가 양쪽에 다시 간다.
