## 실제 설정 및 관리 근거

- production 전체 변수 목록에 `PUBLISH_KEY_SCOPE`와 `PUBLISH_EXPIRES_AT`가 없다. 새 단일키·절대만료 제한이 실제 적용됐다고 말할 수 없으며 업로드 토글만 켜지 않는다.
- 등록된 secret 이름은 `ACCESS_CODE_SHA256`, `ACCESS_SESSION_SECRET`, `NOTICE_TOKEN_SHA256`, `PUBLISH_TOKEN_SHA256`이다. 값은 읽지 않았다.
- `PUBLISH_LIMITER` 편집 화면에서60회/60초를 읽고Cancel했다. 이는 실제 binding 값이며 전세계 합산 요청 예산을 의미하지 않는다. 현재 소스의 notice/publisher 집계 키 차이는 [기존 답안](WS_HOST_ANSWERS_20261023.md)을 참조하되 배포 소스 일치는 별도 확인이다.
- 변경 전 계정 감사로그에서10/16~10/25 00:55 KST·workers·view제외 필터의25개 성공/0실패 기록을 읽었다. 표시된 기록은 모두10/16, 최종 설정PATCH12:39:13·배포CREATE12:39:12가 포함된다. 관리 이력은 서비스 요청 로그가 아니며 과거값/기간 완전성 증거도 아니다. 이번 변경 후 감사 화면에서도 **10/25 01:05:08 KST, update Patch Worker Script Settings, Dashboard** 행을 확인했다. 변경값 전체의 역사나 중간 불변까지 입증하지는 않는다.
- 저장 로그에는 IP/브라우저/네트워크 메타데이터가 포함되고 cookie는REDACTED로 표시됐다. 다른 인증 필드 전체의 마스킹을 검증한 것은 아니다. 공개 기록에는 시각·method·path·status·version만 남기며 원시 로그/접속 주소/개인정보를 옮기지 않는다.

현재 소스 대응을 보기 위해 우리 Worker 편집 화면을 읽기만 열었으나 소스 내보내기/해시 확인은 하지 못했다. 이때 자동 Preview 콘솔에16:13:08 UTC의GET2개가 표시됐다. 수동 재생/편집/코드 배포는 하지 않았고 바로 나왔다. 이 Preview 호출을 production 요청이나 별도 합격 근거로 분류하지 않으며 전체 네트워크 요청 수는 미측정이다.

## 승인 범위와 다음 실행

이전 ‘설정 읽기만’은 사용자 후속 지시로 해제됐다. 구체적으로 제시한 Logs100%·최대3회 무인증 홈 조회 중2회를 실행했다. 승인 대기라고 다시 기록하지 않는다. 다만 새 접속 대상·비밀 전달·실경기·새 공동시험GO까지 자동 승인으로 확대하지 않는다.

다음 배포 후보를 만들 때 dashboard 설정과Wrangler 설정의 관측 옵션을 대조해야 한다. 현재 공용 예제에는observability 선언이 없으므로 새 배포가 오늘 설정을 유지한다고 가정하지 않는다. 배포 소스와 보관 범위가 확정되기 전 공용 기본값을 임의 변경하지 않았다.

권한 회수는 기존 유효 자격으로 성공 확인 → 해당 자격 회수 → 옛 자격 거부를 대조해야 한다. 현재UPLOAD_ENABLED=false에서의503을401회수 증거로 바꾸지 않는다. 관람 회수는접근문ON·noticeOFF·다른유효digest유지 조건이고, 전체삭제503이나로그아웃으로 대신하지 않는다. 긴급 상황은OFF우선이며401을 얻으려고 재개하지 않는다.

**다음 순서:** 새 고정 전달본/검토 결과와 host/runtime 대응 확인 → 단일key·UTC만료·창·원장/양측GO 고정 → 승인 범위의 자격/설정 적용 → 실제 합성 연결·안내·회수 → 비식별 로그 대조. 현재 저장 로그 기반을 확보했지만GATE-06의발행scope/expiry·시험구간연결은HOLD다.
