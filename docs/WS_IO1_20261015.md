# WS-io1 — 알림 저장 실패 뒤 임시 파일 정리

알림 상태를 쓰다가 일부 write 또는 sync가 실패하면 임시 파일이 남고, 재시도 성공 뒤에도 잔류했다.
보고서에서 검증한 소유 확인 함수를 `owned-files.mjs`로 분리해 알림에서도 사용한다.
open·부분 write·sync·rename 오류 때 자신이 만든 임시 파일을 정리하고, 기존 알림 상태와 입력은 유지한다.
정리 자체가 실패하면 `alerts_temp_cleanup_incomplete`로 실패를 숨기지 않는다.

기준 main `33f46aa956d302d193ea288e8b9a38a6e6786d1c`, 구현 `7c81a649358152dc904721f4e92fa6c265af896d`,
R2 작업 병합 후 전체 검사 `71d0a3d9c31d4f84216b8c7794dfc62081c52e39`, 최종 검토 `c19e1c5270b7fc1c6ce1cf46dda4970d675089fb`.

- 새8검사: open/부분 write/sync/rename 실패 후 정리·재시도, 외부 선점·교체 감지 시 보존, 정리 오류, 정상 저장·반복 억제.
- 기존 보고서 실패10검사, 전체 Node243, 체크리스트8, 문법 검사 통과. 보고서 helper 함수 본체의 추출 전후 일치도 확인했다.
- 실행 명령은 영수증에 기록했다. Windows·Node24.1에서 합성 임시 파일과 모의 전송만 사용했다.
- 작성 GPT-6 계열(Codex, 정확한 세션 모델 id 미노출), 다른 모델 gpt-5.6-sol이 구현 검토와 집중18검사를 수행했다.
  최종 문구 수정 커밋에서 로직·테스트 파일 변경 없음을 확인해 PASS로 판정했으며 검사를 반복하지 않았다.

## 독립 검토에서 확인한 한계

처음에는 외부 파일 보존 문구가 지나치게 넓었다. 검토자는 마지막 소유 확인 후 실제 pathname unlink 직전에
외부 파일로 교체하면 `{complete: true, externalExists: false}`가 되는 사례를 재현했다.
이 경합은 수정됐다고 주장하지 않는다. CLI가 협력 잠금을 사용하는 **신뢰 가능한 단일 작성자 작업 폴더**가 지원 범위다.
검사 시점에 발견한 identity/content 불일치는 보존하지만, 마지막 검사와 unlink 사이의 교체는 원자적으로 막지 못한다.
단 한 번의 외부 교체도 이 간격에서 발생하면 삭제될 수 있다. helper 주석과 알림/보고서 운영 문서를 이 범위에 맞췄고,
검토자는 미공개 무조건 보장에 관한 지적을 철회하고 알려진 범위 한계로 남겼다.

강제 종료 원자성, 비협력 동시 작성자 격리, 실제 알림·클라우드 배포는 검증하지 않았다.
팀원 저장소·프로세스·배포는 변경하지 않았다. 기존 WS-report3의 검사 수치는 당시 기록이며 현재 경계는 위와 같다.
