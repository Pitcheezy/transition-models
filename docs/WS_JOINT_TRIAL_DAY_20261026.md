## 3. A — 합성 파일 전송·회수 시험

### 3.1 완료 기준 (착수 전 고정)

1. 실제 사용할 고정 실행 절차와 파일 SHA를 수신·대조했다(새 ZIP 또는 대체 절차; §5 인수 통과).
2. 새 시험 키 1개·정확한 허용 경로·절대 UTC 만료·요청 예산을 비공개 원장에 고정했고 양쪽이 확인했다.
3. 쓰기(PUT/DELETE)는 Song 실행본만 수행했다. 우리는 HEAD/probe·관측·회수만 했다.
4. 모든 실제 요청을 서버 저장 로그(시각·method·path·status·버전)와 1:1 대조했고, 본시험 구간의 배포 버전·설정이 고정돼 있었다. 계획된 회수/종료 변경은 단계별 전후 버전·설정 영수증으로 연결한다(예상 밖 변경은 중단).
5. 합의된 만료 403, 발행 자격 회수 401, 종료 후 업로드OFF 503을 확인했다.
6. 예상 밖 실패·시간초과·결과 불명확이면 그 창에서 중단했고 임의 재시도가 없었다.

증거 필요조건: Song 실행본의 종료코드 0 + wrapper-log `PASS_SYNTHETIC_HTTPS`(PUBLIC-SUMMARY PASS만으로 불인정), 우리 로그 대조 영수증(허용 필드만 공개), 관리 API 조회 횟수 별도 원장. 합성 자료이며 실경기·화면 합격이 아니다.

### 3.4 새 자격 준비 순서 (비밀은 비공개 폴더에만)

1. 다음 창 확정 후 승인된 담당자가 비공개 폴더에서 새 발행 시험 토큰을 만든다(32바이트 난수, base64url). 예: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))" > <비공개>/publish_token_YYYYMMDD.txt`.
2. digest만 계산해 등록한다: `node -e "const fs=require('fs');console.log(require('crypto').createHash('sha256').update(fs.readFileSync(process.argv[1],'utf8').trim()).digest('hex'))" <비공개>/publish_token_YYYYMMDD.txt`. 출력은 digest이며 토큰이 아니다.
3. 원문 토큰은 **기존 사람 간 비공개 채널**로 Song에게 전달한다. 공개 이슈·ZIP·채팅 금지. 이전 시험 토큰은 재사용하지 않는다.
4. 폐기용 digest(시험 뒤 교체용)도 미리 만들어 둔다. 폐기용 원문은 아무에게도 전달하지 않는다.
5. 공개GET이 있으면 A에서도 Song 관람 코드가 필요하다. 같은 방식(8~128자, digest만 등록, 원문 비공개 전달). 본인 복구 코드 digest는 유지한다.
6. 등록 뒤 필요한 로그인/진단 요청도 원장에 별도로 합산한다. 범위 밖403·미사용404를 실행본이 검사하면 우리 쪽에서 중복 호출하지 않는다. 담당자와 정확한 횟수를 GO 전에 확정한다.

### 3.5 요청 원장 — 다음 창에는 v2 사용

[v1](results/ops/ws_trial_day_ledger_template_20261026.json)은 당시 이력으로 보존하며 실행하지 않는다. [v2](results/ops/ws_trial_day_ledger_template_20261026_v2.json)는 수정안이고 합의 전 실행 불가다.

- 자격 준비/login·사전 홈HEAD1·wrapper 범위밖HEAD1·본시험의 모든 HEAD/PUT/GET/DELETE·후속3개·선택 관람회수 요청을 각각 한 행에 적는다. 사전요청이 본시험 상한에 포함되는지 명시하고 총합을 맞춘다. 관리 API 조회/설정은 별도 원장이다.
- 본시험 횟수·시간 상한은 선택 실행본에서 확인하고 합의한다. 과거18회/120초와32회 묶음을 혼용하지 않는다.
- 후속은 **만료403 1회 → 호스트digest교체 신호 → 옛Bearer401 1회 → 호스트OFF 신호 →503 1회**. 한 단계의 재시도로 다른 단계의 몫을 쓰지 않는다. 중단/예산소진 시 미측정으로 남기고 관리 회수는 완료한다.
- 각 행에 소유자·시작/종료시각·method·정확한 경로·기대/실제상태·Ray·ETag·삭제표식·캐시헤더·서버시각·버전을 기록한다. Authorization/Cookie/Set-Cookie는 기록하지 않는다. 없는 헤더는 미확인이지 성공이 아니다.
- 삭제표식 private HEAD는200+X-Publish-Deleted:true+삭제ETag, 공개 HEAD는404다. 이 둘을 비교하지 않는다. 브라우저 자동갱신/주기감시는 본 실행에 섞지 않는다.

### 3.6 정상 종료 순서

1. 본시험 정상 완료 뒤 만료403을 한 번 확인한다. STOP 뒤에는 자동 후속하지 않고, 양쪽이 합의한 후속 범위·남은 예산·단계별 신호가 있는 경우에만 진행한다. 조건이 없으면 추가 요청 없이 관리 회수로 종료한다.
2. 발행 digest를 폐기용 유효digest로 교체하고 적용 버전을 기록한다. 업로드는 이 단계까지ON이다.
3. 호스트 신호 뒤 옛Bearer HEAD401을 한 번 확인한다.
4. 업로드·자료읽기OFF 적용 신호 뒤 HEAD503을 한 번 확인한다.
5. OFF설정 확인 뒤 scope/expiry를 함께 정리하고 오늘 관람digest를 제거한다. 본인복구용 자격은 유지한다. 별도 관람회수 요청 예산이 없으면 HTTP401은 미측정이다.
6. 로그/설정 원장을 연결한다. 예산소진 시 추가 요청 없이 관리 회수·OFF를 끝내고 미검증 상태를 명시한다. 잔여 삭제표식은 보존한다.

### 3.7 긴급 차단 순서

1. 즉시 `UPLOAD_ENABLED=false`. 2. 필요 시 안내 ON(`maintenance`/`data_hold` 고정 문구, 현재 ETag 조건부 PUT, 감사 기록) 및 `DATA_READ_ENABLED=false`. 3. 발행 digest 교체/제거와 적용 버전을 함께 기록. 4. 401 확인은 미완료로 남기거나 별도 창으로 넘긴다(401을 얻으려고 업로드를 다시 켜지 않음). 5. 사유·시각·영향을 비공개 원장에 적고 공개 이슈에는 상태만.

### 3.8 중단 규칙

첫 요청 전 거부·키 미소모면 창 안 재준비1회 제안 가능. 한 번이라도 요청이 나간 뒤 unknown·5xx·429·예상 밖412·시간/예산 초과이면 본시험STOP, 재시도하지 않는다. STOP 후속은 §3.6의 합의·잔여 예산·신호 조건이 있을 때만 가능하다. 새 본시험은 새 키/run_id/승인이며 후속은 단계별1회씩 최대3회다. 다른 단계 예산을 대신 쓰지 않는다. 만료−3분을 넘긴 시작은 하지 않는다.

## 5. 새 ZIP 인수 순서 (받는 즉시)

1. 원본을 별도 비공개 폴더에 보존(덮어쓰기 금지). ZIP 전체 SHA-256·크기, 경로이탈·중복·대소문자 충돌·링크·암호화·CRC·manifest 대조. 불일치면 중단.
2. 등록/실행본/manifest와 source/build·검토 대상이 **같은 최종 커밋**을 가리키는지, runtime5 원본/CR제거 SHA가 우리 고정본과 같은지, 작성·검토 모델 ID·검토 해시·남은 조건.
3. 기존 전달본 대비 변경 목록. "화면/핀만"과 다르면 범위 재확인. 3결함·차단 2건의 수정 주장은 B/§3.2 증거로만 인정.
4. 필요한 로컬 검사만(§4.2). 원본 Windows `verify_offline.py`의 fcntl 실패를 반복·shim하지 않는다. 대규모 검사·영상 분석·전달팩 재포장은 새 결함이 없으면 반복하지 않는다.
5. 통과 뒤에만 우리 후보를 새 폴더로 구성. 실제 배포는 이 절차에 없다.
