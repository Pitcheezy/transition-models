## 요청 원장 — 정상 경로 서비스 HTTP 최대32회 제안

- final2 본 시험: 범위 밖 HEAD1 + 내부runner17 = 최대18. 처음/마지막 HEAD는17 안에 있으므로 중복하지 않는다.
- 후속probe: 만료·발행 자격 회수·업로드OFF, 합계 최대3. 전송 실패 시도도 소모한다.
- 관람: 로그인1 + 관람 자격 회수 뒤 옛 세션 확인1 =2.
- 안내 기능 별도 시험9: GET상태 → PUT ON → GET상태/감사 → GET홈 → GEThealth → 최신 strong ETag로 PUT OFF → GET상태/감사 → GET홈 → GEThealth.
- 순서는 로그인 → 별도 안내9회 → 실행 직전 창/만료여유 재확인 → 본시험/후속 → 관람회수확인이다. 안내OFF의 홈/health는 기존 허용 상태로 복귀했는지 확인하며, 원래 없는 health를200으로 만들려고 추가 파일을 발행하지 않는다. 사전 상태 확보 호출은 추가 사전점검 원장에 넣는다. 이미 켜진 안내를 이 시험 때문에 자동 해제하지 않는다.
- 합계32는 **서비스 정상 경로 제안 상한**일 뿐 전체 비용/전체 요청 합의가 아니다. Cloudflare 조회·secret변경·배포 등 관리 API, 추가 사전점검과 실패 정리는 별도 원장에 실제 횟수/시각을 기록한다. 현재 횟수는 미측정이며0으로 쓰지 않는다.
- 본 실행 중 브라우저 자동 갱신/주기 감시를 섞지 않는다. 이미 열린 화면 반응 검사는 별도 창/별도 원장으로 진행해야 하며32회에 몰래 포함시키지 않는다.
- 추가 호출/자동재시도/실패 정리를 무제한 허용하지 않는다. 실패 예산은 실행 전 합의하고, unknown·예상 밖412·429·시간/예산 초과 시 중단한다. 의도한 낡은 DELETE412는 정상 항목이다.

## 정상 회수 협의안과 긴급 중단

**정상 종료 제안(합의 전 적용 금지):** 본 시험 정리/삭제표식 및 필수 만료 확인을 마친 뒤, 정확한 키·만료 제한은 유지한 채 발행 digest를 새 폐기용 유효 digest로 교체한다. 실제 적용 version/설정 증거를 보존하고 옛 bearer HEAD401을 확인한 뒤 업로드OFF·읽기OFF로 끝낸다. 새 원문은 전달하거나 사용하지 않는다. digest를 전부 없애면503이어서401 증거가 되지 않는다.

**긴급 중단:** 즉시 업로드OFF가 우선이다. 필요하면 안내ON·읽기OFF도 적용하고 자격을 회수한다. 401을 얻으려고 업로드를 다시 켜지 않는다.503은 차단 증거이며 회수의 단독 증거는 아니다. secret교체/제거와 적용 version을 함께 기록한다. 이 상황의401 검사는 미완료로 남기거나 별도 승인 창으로 넘긴다.

관람 digest 제거 후 옛 세션 거부를 확인한다. 접근문ON·noticeOFF·다른 유효digest 최소1개 유지일 때 GET `/`의401을 기대하며, 전체digest삭제/noticeON의503은 이 검사를 대신하지 않는다. logout만으로 복제 쿠키는 회수되지 않는다. 옛 digest 재추가/옛 설정 복원은 세션을 되살릴 수 있으므로 롤백에 자격 상태도 포함한다. 범위 설정은 업로드OFF·자격 회수 뒤 정리한다. 잔여 객체/삭제표식은 보존하고 별도 합의 없이 물리 삭제하지 않는다.

## 비상 안내 스위치 답변

- **배포 여부:** [10/25 본인 시험](https://github.com/Pitcheezy/transition-models/blob/abddb240a698e91923d14ef413e36081a4af5315/docs/WS_NOTICE_TRIAL_20261025.md)에서 고정 runtime·원격 바이트와 안내ON/OFF·동일세션복구를 확인했다. 마지막 상태는 상단을 따른다. 저장 로그1건·최신 Song 화면·양측 권한/공동시험은 미완료다. 시험 안내 자격은 회수했으며 복구 자격은 본인만 비공개 보관한다.
- **토큰:** 안내 전용 `PITCHEEZY_NOTICE_TOKEN`을 비공개 ENV로 읽고 서버에는 `NOTICE_TOKEN_SHA256`만 둔다. 담당자별 digest1~8개, 자동 만료/자동회전 없음. 회수는 제거/교체 후 적용 확인이다. 양측 운영자 권한 전달은 아직 결정/실행하지 않았다.
- **켜고 끄기:** 아래 CLI의 dry-run → 현재 GET 스냅샷 → 현재 ETag로 조건부 PUT → GET/감사/화면 확인. `maintenance` 또는 `data_hold`의 고정 문구만 사용한다. OFF는 복구 판단 이후 별도 명령이다.412/unknown은 자동 덮어쓰기하지 않는다.
- **걸리는 시간:** [10/25 본인 원격 관측](https://github.com/Pitcheezy/transition-models/blob/abddb240a698e91923d14ef413e36081a4af5315/docs/WS_NOTICE_TRIAL_20261025.md)은 PUT ACK 뒤 홈ON3.430초·OFF3.211초다(의도한2.1초 대기 포함). 최초 전환/전세계 CDN 전파 상한·운영RTO·이미 열린 Song 화면 갱신 지연은 미측정이다. 이전 loopback 수치는 별도 이력이다.
- **범위:** 안내는 페이지·자료를503으로 막지만 업로드·관리경로는 살아 있다. 기존 final2/v4.4 수신 화면은 이미 열린 경우 안내와 과거 추천이 함께 남는 현상을 확인했다. 새v7/v4.5의 수정 보고는 수신 뒤 별도 검증해야 한다. 새로운 접속/새로고침은503 안내로 막혔다. 완전한 화면 철회가 필요하면 Song 화면 수정/판정이 필요하다.

```text
node ops/public-host/notice-cli.mjs --plan <비공개-GET계획.json>
node ops/public-host/notice-cli.mjs --plan <비공개-GET계획.json> --execute --snapshot <새-비공개-상태.json>
node ops/public-host/notice-cli.mjs --plan <현재ETag를넣은-ON계획.json>
node ops/public-host/notice-cli.mjs --plan <현재ETag를넣은-ON계획.json> --execute
node ops/public-host/notice-cli.mjs --plan <비공개-GET계획.json> --execute --snapshot <새-비공개-ON후상태.json>
# 사람이 복구를 결정한 뒤 새 ETag를 넣은 OFF 계획으로 같은 순서를 따른다.
```

계획의 정확한 JSON은 [안내 CLI](../ops/public-host/notice-client.mjs), [운영 절차](../ops/public-host/NOTICE.md)를 따른다. 명령은 준비용이며 이번에 실제 대상에 실행하지 않았다.

## 결과 인수

종료코드·wrapper-log·공개요약·호스트 실제 상태코드를 함께 대조한다. `MAIN_PASS_INCOMPLETE`는 합격이 아니다. `SECRET_FOUND_IN_OUTPUT`/비0종료/실패 로그이면 공개 요약의 PASS 문구만 보고 공유하지 않는다. 그 분기는 조건부 정적 소견이며 실행 재현은 하지 않았다.

합성 결과와 실제 경기 결과를 구별한다. 운영 기록의 원본 비밀/주소/개인경로를 제거한 회신 초안을 만든 뒤 발신 승인을 받는다. 상대 #38이나 우리 #18을 준비 완료만으로 닫지 않는다.
