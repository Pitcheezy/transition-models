# WS-report3 — 보고서 저장 실패 복구

두 번째 JSON 파일 생성 실패가 먼저 쓴 Markdown을 남겨 이후 재시도를 막던 문제를 수정했다.
기존 출력 또는 경합한 외부 파일은 보존한다. 출력쌍 독점 잠금과 생성 파일 식별/내용 검사 후 롤백을 적용했다.
Windows Node24.1의 handle stat와 경로 stat의 dev 값 차이를 실제 확인해 같은 API끼리 비교하며,
큰 inode 값은 bigint로 보존한다. 입력/출력 스키마와 정상 성공 파일명은 그대로다.

기준 main `cc0bf1726826d043068bd9519d50bb71c924908e`, 고정 구현 `83736786991af0cca8fe942e2d55adf371d3168a`.
합격 기준은 [우리 board 선점](https://github.com/Pitcheezy/transition-models/issues/3#issuecomment-6189189968)에 먼저 기록했다.
[운영 절차](../ops/public-host/REPORT.md), [명령·파일 SHA·검토 영수증](results/ops/ws_report3_20261015.json).

- 집중 오류 주입10 + 기존 보고서14 = 24검사 통과.
- 전체 Node223, 체크리스트8, 문법 검사 통과. Windows workerd socket-close 진단은 있었지만 검사 실패는 없었다.
- 작성 GPT-6 계열(Codex, 정확한 세션 모델 id 미노출), 독립 검토 gpt-5.6-sol이 고정 구현을 읽고 집중24검사 실행: PASS, 지적 없음.
- 전원 차단/강제 종료의 두 파일 원자적 저장이나 지속적인 외부 파일 교체와의 완전 격리는 보장하지 않는다.
- 실제 배포/실서비스 프로세스/팀원 저장소/외부 발신은 변경하지 않았다.

잔여 잠금은 자동 삭제하지 않는다. 실행 여부와 출력쌍을 확인하고 증거를 보존한 뒤 새 빈 폴더에서 재실행한다.
이번 합성 검증을 실경기 운영 또는 실제 클라우드 복구 증거로 쓰지 않는다.
