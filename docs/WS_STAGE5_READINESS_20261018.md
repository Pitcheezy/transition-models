# WS-stage5 — 양쪽 서비스 연결 점검 실행 준비

2026-10-18. 기준 main `9e405aa195dc914f228102e4584ffe85f187c704`, 선점 `03ae493`.
[사전 합격 기준](https://github.com/Pitcheezy/transition-models/issues/3#issuecomment-6247513227).
**완료 범위는 비공개 후보·로컬 검사·실행안이다. 실제 계정 조회·배포·Song 접속 허용·키 발급·mail 발신은 하지 않았다.**

## 무엇을 연결하는가

Song의 실행기가 작은 가짜 JSON 한 개를 우리 시험 호스트에 올리고, 읽기·수정·삭제표식·자격 회수를 확인한다.
추천 모델 성능, 실경기, 팬 공개 서비스의 합격 시험이 아니다. 작업 완료 후 결과를 COLLAB-001에 기록하는 것도 발신 승인 범위에서만 한다.

- **연결 점검:** 한 키, 본문 2KiB 이하, runner 17회 정상 경로. 실제 전송 경로와 조건부 갱신이 대상이다.
- **화면 점검:** 받은 경기 예제는 약35~38KB로 2KiB를 넘고 목록·health 등 여러 키가 필요하다. 따라서 한 키 시험과 별도로 검사한다. 이번에는 Windows 새 loopback에서만 진행한다.
- **실경기 운영:** 다중 파일 발행 범위·감시/양쪽 알림·연락/권한·최신 화면/계약·권리 및 실제 경기 승인을 별도 확정해야 한다.

[기존 수신 감사](WS_PARTNER_V42_20261018.md)와 [협업 규약](COLLABORATION_PROTOCOL.md)은 유지한다. 사람 검토/A-y·모델 이식은 이 연결 점검의 선행 조건이 아니다.

## 받은 화면과 우리 Worker의 로컬 통합 결과

새 loopback Miniflare에서 우리 실제 Worker/R2/접근문과 받은 화면을 함께 실행해 **22항목 통과**했다. host runtime5개는 후보와 LF 정규화 동치, 화면4개는 원본 바이트 동일이다. Windows Node24.1.0, Edge155, 기존 고정 Miniflare/Playwright를 사용했다.

- 접근문401 → 브라우저 로그인 → 원본시각 지연표시 → 별도 시각이동 예제의 추천·실제결과 표시.
- held_last_accepted 정정 결과 유지, 미확인 공/미지원/연결 끊김 구분.
- health만 갱신 시 game GET1→1, 파일순번 증가 시1→2. 원문 readback SHA/ETag·304 통과.
- 철회404 → 전체 새로고침 후 이전 추천 없음 → 복구 후 표시 → 로그아웃 후401.
- 30.155초, **105 HTTP요청 시도**(검사41+브라우저64), 외부 요청·구형 API·브라우저 예외0. 자체 브라우저/서버 종료, 원본22파일 불변.

이 검사는 여러 키·약44KB 파생 예제·로컬600회/60초 제한으로 수행했다. 실제 한 키2KiB/18회 시험과 다르다. 목록3종은 우리 합성 보조자료이고, 시각/sequence 변경 예제도 별도 파생본이다. 게이트401·조건부304·철회404는 의도한 응답이며 모든 요청이2xx라는 뜻이 아니다.
철회 화면은 **전체 새로고침 후** 확인했다. 이미 열린 화면의 자동철회 지연, 관리자 자격 회수/만료, CDN/TLS, Song runner, 실기기는 미측정이다. 화면 캡처·원문·검사 harness는 비공개 outputs에만 있다.

## 시작 전 확정할 한 장

다음 값이 없으면 실행하지 않는다. 문서 준비와 실제 연결 승인을 구분한다.

- 대상: 기존 전용 시험 자원만, 우리 담당+Song 실행 담당. 기존 서비스·DNS·유료 전환·일반 공개는 제외.
- 고정 파일: 위 후보·화면 SHA, 받은 runner가 요구하는 **우리 gateway pin** `48ec406589982547e298ff2ee4bc2d64ed0216c0`(runner 자체는 전달 소스57f5d3f 표기). 현재 host의 runtime5파일 Git blob이 그 pin과 같다는 수신 감사와 실제 배포 version ID를 따로 기록.
- 시간: KST 시작/종료와 UTC 절대 만료를 비공개 실행표에 고정. 시간 미정. 남은 유효 시간이 부족하면 시작하지 않으며 runner120초 제한과 만료 전 정리 여유를 함께 계획.
- 작성자: Song 리허설 runner 하나만 해당 키에 쓴다. 우리 전송기·재시도·다른 publisher가 동시에 쓰지 않는다. 본 점검에는 자동 화면 폴링/주기 감시를 끼우지 않도록 담당자가 별도 합의한다. 우리 AI가 상대 프로세스를 중지하지 않는다.
- 자격: 발행 bearer, 별도 Song 관람 코드/세션, 우리 운영자 권한을 분리. Cloudflare 편집 권한은 상대에게 전달하지 않는다. 새 자격 전달·회수는 비공개로 수행.
- 연락: 준비 작업에는 실시간 연락이 필요 없다. 실제 연결 창에는 두 담당자의 시작/중단 확인 수단·응답 가능 여부가 필요하며 아직 확정되지 않았다.

## 요청 원장과 합의가 필요한 제한

기존 제안은18회/120초/본문2KiB다. 이를 임의 확대하지 않는다. 로그인부터 회수까지 정상 경로의 **합의 후보 하한**은 아래20회이며, 사전점검·장애 조사·관리 API는 추가 기록 대상이다.

1. 임시 관람 세션 로그인: 서비스 HTTP1회.
2. Song runner 정상 경로: 서비스 HTTP17회. 첫 HEAD(미사용 키), 마지막 HEAD(삭제표식)가 이미 포함된다. 별도 중복 확인을 하지 않는다.
3. 종료 뒤 옛 발행 자격으로 같은 키 HEAD: 서비스 HTTP1회.
4. 회수한 옛 관람 세션으로 보호된 JSON GET: 서비스 HTTP1회.

이20회는 사전점검을 제외한 부분합 제안이며 아직 승인되지 않았다. notice 상태 확인 등 추가 요청까지 합친 전체 원장을 양쪽이 확정해야 한다. 로그인·종료확인을 다른 단계로 나누더라도 총량을 숨기지 않는다. 앞선19회는 관람 세션 회수 확인을 제외한 최소 계산이었다. 브라우저를 열면 asset·polling 등이 추가되므로 이 원장에는 자동 화면을 포함하지 않는다.
Cloudflare 버전 조회/배포/secret 변경 등 **관리 API 요청**은 서비스 요청과 별도 원장에 실제 횟수를 기록한다. 미측정을0회로 바꾸지 않는다. 실패 시 허용할 정리 요청/시간 예산과 관리자 조치도 시작 전에 합의해야 한다. 호스트의60회/60초 limiter는 runner 총량/비용 상한이 아니다.

## 승인 후 순서 — 이번에 실행하지 않음

1. **우리 담당:** 실제 계정/전용 자원·현재 version·vars/bindings/secret 이름·제한값을 읽고 비공개 기록. 마지막 확인은10/16이므로 현재 상태라고 복사하지 않는다. 코드/설정 변경 전 상태를 남긴다. notice 현재 상태·ETag도 확인하고 요청을 사전점검 원장에 센다. noticeON이면 게이트보다 먼저503이므로 자동 해제하지 말고 시작 보류/별도 결정을 한다.
2. 실제 미사용 키·유효 만료·자원 식별자로 새 후보를 만들고 재검사. 같은키 여부는 runner 첫 HEAD에서 판단하며 기존 객체/삭제표식이 있으면 시작하지 않는다. 기존 후보를 실설정으로 덮어쓰지 않는다.
3. 검토된 runtime과 화면을 전용 시험 자원에만 배포. gateON·읽기/업로드OFF·수집/피드백OFF로 먼저 확인. 실제 version ID·vars·자원 및 source hash 대응을 기록. secret 변경도 원격 배포임을 포함한다.
4. 승인된 새 발행 digest와 Song 전용 관람 digest를 준비하고 실제 단일키·만료·gate를 확인한 뒤에만 점검 기간 읽기/업로드ON. 실제 값은 로그·명령 인수·공개 이슈에 쓰지 않는다.
5. Song 담당이 로그인 후 자기 Mac에서 runner를 실행. 우리 노트북은 배포/수신 감시/철회 담당이다. 우리 환경에서 fcntl을 우회하거나 Song Mac에 접속하지 않는다.
6. 정상 경로는 만료 전에 조건부 삭제표식과 runner의 마지막 HEAD까지 완료. 실제 상태코드·바이트·요청수·시각·정리 여부를 양쪽 기록으로 대조한다.
7. 종료 즉시 우리 담당이 업로드OFF → 옛 발행 digest 제거/교체 → 범위 정리 순서로 회수. 이후 scope를 제거하거나 옛 버전으로 되돌리면서 옛 bearer가 다시 살아나지 않는지 설정에서 확인한다.
8. Song 전용 관람 digest 제거, 옛 관람 세션 거부 확인. 우리 담당 코드가 남아 있으면 정상401을 기대할 수 있고 전체 코드가 없으면503 설정닫힘일 수 있다. logout은 한 브라우저 쿠키 삭제일 뿐 전체 회수가 아니다. 전체 세션 비밀 회전은 다른 사용자까지 종료하므로 기본 조치로 자동 실행하지 않는다.
9. gateON·읽기/업로드/수집/피드백OFF를 최종 확인. 시험 자원은 보존하고 물리 삭제하지 않는다. 반환/공개 원문에서 비밀·주소를 제거한 뒤 승인된 범위에서 #18 결과를 남긴다.

## 중단·만료·복구 판정

- 미사용키 실패·잘못된 SHA·예상 밖 상태·실행표에 예정되지 않은412 충돌·unknown·시간/요청 예산 초과 시 runner를 멈춘다. 의도한 낡은 삭제의412는 정상 검사항목이다. 새 ETag 자동조회 뒤 덮어쓰기/반복재시도/물리삭제로 통과시키지 않는다.
- 저장 여부를 모르는 응답 또는 만료 후 정리 실패는 **미정리/확인 불가**로 기록한다. 만료 뒤 같은 자격으로 DELETE할 수 없다. 업로드 차단·자격 회수·증거 보존 후 우리 계정 담당자가 별도 승인된 복구를 결정한다.
- `UPLOAD_ENABLED=false` 또는 digest 누락이면 인증 비교 전503이다. 따라서 옛 bearer HEAD503은 **차단 증거**이며 영구회수의 단독 증거가 아니다. 옛 digest의 비밀값을 원격에서 출력하는 것이 아니라, 해당 secret 이름의 삭제/교체 성공과 실제 적용 version/설정 증거를 함께 기록한다. 401을 받으려고 업로드를 다시 켜지 않는다.
- 삭제한 관람 코드 digest를 재추가하면 아직 만료되지 않은 옛 세션이 재활성화될 수 있다. 롤백은 코드뿐 아니라 자격 상태를 함께 확인하고 옛 digest를 복원하지 않는다.
- 안내ON은 업로드를 막지 않으며 이미 내려받은 화면/자료도 회수하지 못한다. 업로드OFF·읽기OFF·관람회수의 각각을 확인한다.
- 종료 결과는 성공/실패/unknown과 자격차단·설정회수·객체정리를 분리한다. 어느 하나 미확인이면 전체완료로 보고하지 않는다.
