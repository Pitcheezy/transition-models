# 공개 운영 절차 — WS-ops4e

새 [협업 규약](../../docs/COLLABORATION_PROTOCOL.md)이 운영 결정 기준이다.
10/20까지 연락/응답 시간을 정하고, 10/21 이후 고장 수리만 한다. 실제 운영 전 다른 모델 검토가 필요하다.
문제 때 양쪽 담당 사람 누구든 사전 승인 문구로 안내 화면을 띄우고 사유를 이슈에 남길 수 있어야 한다.
전체 화면 안내 스위치는 [WS-safe1](NOTICE.md), 관람 접근 문은 [WS-access1](ACCESS.md)로 로컬 구현·합성 검증했다(실제 문구·전환·토큰·코드·대상은 사람 결정). 기존 JSON 토글만으로 충족하지 않는다.
발행 중단은 양쪽 알림, 맥미니 원인은 Song·호스팅 원인은 우리 우선 조사, 경기마다 이용/문제 기록을 남긴다.
실제 채널·실경기 연결·다시 공개는 사람 결정 범위 안에서 수행한다.


이 문서는 우리 호스팅 후보의 **운영 준비**다. 현재 실제 Cloudflare 계정 배포·비밀 설치·데이터
연결·복구는 수행하지 않았다. 코드의 로컬 검사 통과와 실제 운영 성공 기록을 구별한다.
Song의 모델·발행기·수집 프로세스는 담당자가 관리하며 우리 작업으로 변경하지 않는다.

## 배포 전 준비할 기록

- 운영자와 대체 담당자, 대상 계정·Worker·private R2·D1의 비공개 목록.
- 우리 host와 Song 화면의 고정 커밋, 공급된 계약/validator, 빌드 명령/버전, ZIP 및 manifest SHA.
- 검사한 host/wrangler.deploy.json·public/collection-settings.json의 SHA와 실제 적용 설정 대조.
- 허용 도메인·공개 범위, 동의/기록 안내, 보관일, 이용 기록/피드백 토글 각각의 승인.
- 월간 USD 예산, 알림 임계점·받는 사람, 사고 때 데이터를 닫을 권한. 현재 모두 미확정.
- 이전 정상 Worker 버전과 대응하는 설정/화면/데이터 계약, 데이터 복구점, 마지막 복구 연습 시각.
  Git 커밋은 Cloudflare Worker version ID가 아니며 둘을 연결해 기록한다.

공개 이슈에는 작업 ID·비밀 없는 커밋·SHA·상태만 남긴다. 접속 주소·계정 식별값·토큰·
DB 원문은 비공개 운영 기록으로 분리한다. 토큰은 환경/비밀 저장소에 두며 CLI 인자/URL에 넣지 않는다.

## 출시 순서와 통과 조건

1. [패키지 검사](RELEASE.md)와 [설정 검사](CONFIG_CHECK.md)를 고정 후보에 수행한다.
   산출물 폴더에 다른 파일을 섞지 않는다. 검사 후 수정 시 같은 후보라고 부르지 않고 다시 검사한다.
2. 계정 담당자가 private R2·D1·제한된 비밀·서로 충돌하지 않는 limiter namespace를 마련한다.
   R2 public domain/r2.dev를 켜지 않는다. D1 migration과 UTC03:17 정리를 별도로 확인한다.
3. 별도 비공개 staging에서 실제 전달 예제를 사용한다. 실제 계약 검증은 WS-ops2이고
   현재 전송기의 schema_validated=false를 성공한 계약 검사로 해석하지 않는다.
4. 결과 공개 전/후, 미지원·기권·setup 없음·지연·정정·철회·재시작/중복/충돌을 확인한다.
   파일별 ETag는 여러 파일의 같은 발행 묶음이나 투구 공개 시점을 보장하지 않는다.
5. 실제 화면이 collection-settings.json을 읽어 독립 UI 토글과 보관일에 적용하는지 확인한다.
   설정 검사 통과만으로 읽는 코드가 생기지는 않는다. raw 쿠키·IP·URL을 앱 DB에 기록하지 않는다.
6. 실제 CDN의 GET/HEAD/Date/Age/no-store/404 및 인증 실패·429/412·철회를 검사한다.
   Chrome/실제 Safari/모바일을 구분한다. Windows WebKit omit 쿠키 전송 한계는 여전히 별도 항목이다.
7. [감시](MONITORING.md)에 확정한 health 시각 필드를 넣고 장애·복구를 검증한다. 접근 문을 켤 계획이면 감시 전용 코드를 목록에 넣고
   감시 실행 환경 변수에만 두며 `access_code_env`로 가리킨다(WS-monitor2). 공개 수집 설정 `accessGate`를 게이트와 맞춘다(WS-access3).
   현재 CLI는 단발 실행이다. 상시 프로세스/스케줄·외부 알림·재시작은 별도 연결해야 한다.
8. 계정 소유자가 공개 전환을 수행하고 Worker version·양쪽 커밋·계약·SHA·검사 기록을 묶는다.
   CPU·요청·R2·D1 실제 사용량과 다음 투구 전 표시 비율을 별도 관찰한다. 출시 날짜는 아직 미확정이다.

실제 배포의 정확한 Wrangler 버전과 실행 경로는 아직 고정하지 않았다.
이 문서만 보고 임의 최신 npx 배포 명령이나 기존 Sites 교체를 실행하지 않는다.

## 장애 때 먼저 구별할 것

- 화면 전체 불통: DNS/TLS/Worker/asset 제공 경로를 각각 확인한다.
- 화면은 열리나 JSON 503: DATA_READ_ENABLED 또는 저장소 상태를 확인한다.
- health HTTP200이지만 발행 시각이 오래됨: 발행 중단/피드 지연으로 취급한다.
  Date/Age는 HTTP 응답의 상태이며 데이터가 새롭다는 증거가 아니다.
- 추천 의미나 투구 대응이 잘못됨: 최신 타임스탬프나 정상 HTTP로 덮지 않는다.
  해당 경기를 내려 확인 중으로 표시하고 Song에게 근거를 전달한다.
- 접속 코드 유출 의심: [접근 문](ACCESS.md)대로 새 코드 digest를 추가하고 옛 digest를 지운다(옛 세션 종료). 전체 종료는 세션 비밀 회전이다.
- 수집만 장애: TELEMETRY_ENABLED와 FEEDBACK_ENABLED를 따로 끌 수 있다.
  관전 데이터는 별도 경로이므로 통계 장애 때문에 추천 값을 만들어 대체하지 않는다.

현재 gate의 효과는 gateway.mjs·telemetry.mjs·worker.mjs에 구현되어 있다.
UPLOAD_ENABLED=false는 인증 업로드를 막고 DATA_READ_ENABLED=false는 공개 JSON 읽기를 막는다.
**네 토글을 모두 꺼도 정적 화면 자체는 남는다.** 전체 화면을 안내로 바꾸려면 [긴급 안내 스위치](NOTICE.md)의 운영자 PUT을 쓴다
(현재 ETag 조건부, 감사 기록 자동). 내린 뒤 사유·시각·영향을 이슈에 남기고, 복구는 사람 결정 뒤 같은 경로로 끈다.
기능 OFF와 안내 ON 모두 전체 요청 과금 중단 또는 월간 비용 상한이 아니며, 이미 내려받은 자료를 회수하지 않는다.

## 잘못 발행한 경기 자료

1. 공개 피해 범위·마지막 정상 SHA·발행 순번·지금 ETag를 비공개 기록에 확보한다.
2. 담당자가 [안내 스위치](NOTICE.md)를 켜거나(화면 전체) 계정 운영자가 필요 범위의 공개 읽기를 일시 닫는다. 이미 내려받은 브라우저 자료를 회수했다고 말하지 않는다.
3. 공개 계약에서 먼저 내릴 목록/본문/setup의 순서를 Song과 확인한다.
   우리 전송기는 파일별 조건부 저장만 제공하므로 임의 순서의 다중 파일 원자성을 주장하지 않는다.
4. 단일 파일 철회는 인증 DELETE + 현재 If-Match로 tombstone을 저장한다.
   전체 업로드를 껐다면 이 인증 DELETE도 차단된다. 정정 통로를 다시 열기 전 오작동 발행기의 권한/상태를 해결한다.
5. 412는 중단·대조 대상이다. 최신 ETag를 읽고 같은 낡은 JSON을 자동 재전송하지 않는다.
6. 복원은 검토된 공개 JSON을 tombstone의 현재 ETag로 PUT한다. If-None-Match:*로 복원하지 않는다.
7. 공개 GET의 원본 SHA·투구 키·발행 상태·정정 이력과 실제 화면의 숨김/표시를 확인한 후 공개한다.

현재 소스는 원본 버전을 자동 보관하지 않는다. 공개 파일을 다시 발행하는 논리 복구와
R2 내부 객체를 통째로 복구하는 저장소 복구를 구별한다. 후자는 UUID 헤더와 customMetadata까지
보존한 전용 백업이 필요하며 아직 실계정 복구 연습을 하지 않았다.

## 업로드 토큰 유출 의심

계정 운영자가 UPLOAD_ENABLED를 끄고 발행 담당자에게 중지를 요청한다.
비밀을 회전한 뒤 새 토큰만 제한된 비공개 경로로 전달하고 이전 토큰이 거부되는지 확인한다.
Worker 설정의 digest와 발행기의 원문 토큰을 구별한다. 로그에 원문을 출력하지 않는다.
그동안 바뀐 파일/ETag/내용은 따로 검사한다. 토큰 교체만으로 이미 잘못 쓴 자료가 복구되지 않는다.
롤백 버전의 이전 비밀/토글이 되살아나지 않는지도 다시 확인한다. 자동 회전 기능은 아직 없다.

## 코드 롤백

이전 정상 버전의 화면·코드·설정과 현재 데이터 계약/DB 스키마가 호환될 때만 선택한다.
대상 Worker와 version ID를 대조하고 계정의 Deployments에서 고정 버전으로 되돌린 뒤
JSON 계약·토글·비밀·정리 cron·실제 화면을 재검사한다.

Worker 롤백은 연결한 R2/D1의 자료를 되돌리지 않는다. 이전 코드가 바뀐 자료 구조를 읽지 못할 수도 있다.
삭제된 binding은 롤백을 막을 수 있다. 이 제한은
[Cloudflare 롤백 문서](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)에 따른다.
우리 gateway/telemetry에는 데이터 롤백 경로가 없으며 실계정 롤백 성공은 미측정이다.

## D1 손상·잘못된 migration

통계/피드백 수집을 끄고 현재 복구점·사고 시각·만료 기준·당일 budget을 보존한다.
복원 범위와 손실될 최근 기록을 확인한 계정 소유자가 복구 여부를 결정한다.

[Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)은 지원 DB의 과거 시점
복구 수단이며 Paid30일/Free7일 범위를 문서에서 확인했다. 복원은 기존 DB를 덮고 실행 중 쿼리를
취소한다. 임의로 실행하거나 단순 읽기 명령처럼 다루지 않는다. 실제 계정의 지원 상태는 미확인이다.

복구 후 새 쓰기는 계속 막고 schema·필수 index·만료 삭제·당일 budget·중복 ID 정합을 확인한다.
복원으로 만료된 기록이 다시 나타나거나 당일 상한이 되감기지 않게 점검한다.
정상 정리 cron은 수집 OFF에서도 계속 필요하다. 복구를 위해 잠시 중단했다면 복구 직후 현재 시각
기준 만료 정리부터 확인한다. DB 백업은 공개 R2/공개 asset 폴더에 두지 않는다.

## 완료로 기록할 기준

- 실제 장애 원인과 영향 범위, 조치자·시각, 전후 Worker version/커밋/설정 SHA.
- 데이터가 바뀌었다면 원본/복구 SHA·ETag·계약 검증 결과. 비밀값은 제외.
- 실제 브라우저에서 공개 전후·미지원·setup 없는 상태 확인.
- 감시의 연속 회복 판정과 발행 시각, 외부 알림 도착 여부.
- 실제 회복 시간(RTO)과 잃은 자료 범위(RPO). 지금은 모두 미측정이며 숫자 목표도 미합의.
- 남은 위험·다음 담당. 확인하지 못한 것은 미확인으로 남긴다.

현재 자동 회귀는 파일 단위 충돌·철회/복원·로컬 감시와 [정상 종료 후 영속 재시작/키 회전/수집 OFF 정리](LIFECYCLE.md)를 검사한다.
[로컬 리허설](REHEARSAL.md)의 결과를 실제 CDN/계정 재해 복구 완료로 바꾸지 않는다.
