# songskin — 형 화면(c47)에 색과 3D 타자를 얹는 소스 (넘김 안내, 2026-11-13)

형(Song)의 요청(SongRoute/pitcheezy 38번 이슈, 11/13 15:31 글)에 따라 색 CSS, 3D 타자 스크립트, 우리가 바꾼 index.html을 저장소에 올린다. 형이 이 소스를 자기 빌드에 넣겠다고 했다. 이 폴더의 어떤 것도 배포되어 있지 않다. 우리 쪽에서는 11/12 되돌림 뒤로 공개 앱에 올린 것이 없다.

색만 얹는 판은 [`theme-only/`](theme-only/README.md)에 따로 있다. 3D에 문제가 있을 때 쓰는 대안이다. 그 폴더의 `pz/pz-theme.css`(4,640 B)와 `index.html`(712 B)은 이 폴더의 `pz-theme.css`(5,483 B), `index.html`(926 B)과 이름과 배포 자리가 같지만 다른 파일이다(3D 상자 규칙과 3D 태그가 빠져 있다). 3D를 넣을 때는 이 폴더의 것만 쓴다. 그 폴더 README의 "3D 타자는 이번에 넣지 않는다"는 11/12에 쓴 글이다.

## 3D 모델 파일

모델 파일(`.glb`)은 이 저장소에 넣지 않는다. 형은 비공개로 따로 보내 달라고 했다. 후보는 둘이고, 어느 쪽을 쓸지와 전달은 아직 정하지 않았다(모델 선택(A/B)). 놓는 자리는 `pz/batter3d/assets/`다.

형이 요청한 항목 가운데 파일 이름, 크기, SHA-256은 아래 표에 있다. 어디서 받은 모델인지와 전시·공개 웹에 써도 되는 조건인지는 이 공개 저장소에 적지 않는다(3D 모델 관련 확인은 비공개 기록). 받은 모델 파일과 A의 설명 파일은 공개 저장소에 올리지 않는 것을 전제로 한다.

|---|---|---:|---|---|
| A. 사람형(외부 구매 모델) | `batter-ctl.glb` | 3,212,124 | `c56571c4f831473baa54f3c6e921393309fe287bf69d6803c5c4fe8fd1f67890` | `batter-ctl.meta.json` 12,860 B, `804cceda43eb971691b87eadd46a6a16b2ffefd5e94e03d57283a2b8aae7271c`. 저장소에 없다. 모델을 전할 때 함께 전해야 한다 |

- "설명 파일"은 `모델 이름.meta.json`이다(카메라, 배트, 동작 구간 설정). 형이 요청한 모델 문서와는 다른 것이다. 모델 파일과 같은 폴더에 같은 이름으로 둔다(예: `pz/batter3d/assets/batter-ctl.glb` 옆에 `batter-ctl.meta.json`).

- B에는 "안 치는 공 반응"과 "안타 뒤 달려 나가기" 동작이 없다. 볼과 루킹 스트라이크에서는 가만히 서 있고, 안타도 일반 타격 동작으로 보인다.

## 우리가 바꾼 index.html (926 B)

형의 c47 `index.html`(659 B)에 세 가지를 넣은 것이다.

1. 형의 모듈 스크립트 앞에 import map 한 줄: `three` → `./pz/batter3d/vendor/three.module.js`, `three/addons/` → `./pz/batter3d/vendor/addons/`
2. 형의 CSS 링크 뒤에 `./pz/pz-theme.css` 링크와 `./pz/pz-batter.js` 모듈 스크립트
3. `theme-color` 값을 `#f5f7f8`에서 `#091811`로

이 파일은 c47 빌드의 자산 이름(`index-X1sSTTQ4.js`, `index-ks_hu7Ji.css`)을 그대로 적고 있다. 자산 이름이 다른 빌드에 이 파일을 그대로 쓰면 빈 화면이 된다. 새 빌드에서는 그 빌드의 index.html에 위 세 가지를 넣으면 된다.

## 형의 빌드(번들러)에 넣을 때 알아야 할 것

우리가 돌려 본 것은 한 가지 방식뿐이다. 빌드가 끝난 결과물 옆에 `pz/` 폴더를 위 표의 자리대로 두고 index.html에 세 가지를 넣는 방식이다. 이 파일들을 형의 소스에 넣어 함께 번들하는 방식은 돌려 보지 않았다. 아래는 그때 달라질 것으로 보이는 점이고 코드로 읽은 것이다.

- **three.js:** `batter3d.js`는 `three`와 `three/addons/loaders/GLTFLoader.js`를 이름으로 가져온다. 번들러에서는 npm의 `three@0.187.0`을 쓰면 import map과 `vendor/` 폴더가 필요 없다.
- **모델 폴더 위치:** `pz-batter.js`는 `new URL("./batter3d/assets/", import.meta.url)`로 모델 폴더를 찾는다. 번들한 뒤에는 이 기준이 묶인 파일의 주소로 바뀌므로, 모델 폴더가 그 옆에 놓이게 하거나 이 줄을 실제 주소로 바꿔야 한다.
- **색 CSS와 스크립트는 같이 넣어야 한다.** 3D 상자의 크기와 자리(140×210 px, 존 행 바깥으로 22 px)는 `pz-theme.css` 끝부분에 있다. CSS 없이 스크립트만 들어가면 타자가 작게 그려지고 실루엣은 숨는다(아래 "알려진 문제" 3).
- **`pz-theme.css`는 형의 CSS보다 뒤에 읽혀야 한다.** `--sv-*` 색 토큰과, 색을 직접 적은 형 규칙 일부를 같은 선택자로 덮어쓴다(선택자는 파일 안에 있다). 순서가 앞서면 색이 바뀌지 않는 곳이 생긴다(돌려 보지는 않았다). 크기와 간격은 바꾸지 않는다. 3D와 관련해서는 `.sv-zrow.held`(3D를 흐리게)와 `.sv-batband .sv-batter`(실루엣 윤곽선 색)도 쓴다.
- **형 화면에서 읽는 것과 손대는 것:** `pz-batter.js`는 형 코드를 바꾸지 않는다. 문서 전체에 MutationObserver 하나를 걸어 그려진 화면(DOM)을 지켜보고, 화면에는 세 가지만 손댄다. `.sv-zrow` 안에 `div.pz-bat3d` 상자를 넣고, `.sv-zrow`에 `pz-has3d` 클래스를 붙이고, `.sv-batband` 안의 `svg`에 인라인 `visibility: hidden`을 건다. 3D가 실패하거나 풀리면 셋 다 되돌린다. React가 `.sv-zrow`의 클래스를 다시 쓰면 다음 틱에 다시 붙인다. 확인용으로 `window.PZSongSkin`도 만든다. 아래 이름이 바뀌면 3D가 붙지 않거나 반응하지 않는다.
  - `.sv-game .sv-zrow`와 그 클래스 `bat-r`(있으면 우타자, 없으면 좌타자로 본다), 그 안의 `.sv-batband`(실루엣이 놓이는 자리. 없으면 3D도 숨긴다)와 그 안의 `svg`(실루엣)
  - `.sv-game .sv-actual-line`("실제 투구" 줄)과 그 안의 `.sv-g1`(클래스 낱말 `ball` / `strike` / `inplay`), `.sv-al-label`, `.sv-actual-name`, `.sv-tag`, 줄 바로 아래의 `span`들(결과 글)
  - 결과 글의 낱말: 헛스윙, 파울, 홈런, 안타, 1루타, 2루타, 3루타, 아웃, 실책, 병살, 선택
  - `.sv-zrow`가 `<main>` 안에 있고 그 `<main>` 안에 `.sv-actual-line`이 있을 것(다르면 첫 화면에서 동작이 한 번 재생된다. 코드로만 읽었다)
  - `.sv-zrow`가 `position: relative`이고 `--sv-zone-mid` 값을 갖고 있을 것(3D 상자의 세로 자리)
- **내려받는 시점:** 지금 방식은 `pz-batter.js` 태그가 모든 화면이 같이 쓰는 index.html에 있고 `batter3d.js`와 three.js를 정적 import로 가져온다. 그래서 3D 코드 전체(JS 7개, 압축 전 약 2.35 MB)를 경기 목록 화면에서도 받는다. 모델 파일과 설명 파일만 경기 화면에서 받는다. 번들러에서는 존 행이 나타난 뒤에 불러오는 방식(dynamic import)이 맞을 것으로 보이지만 해 보지는 않았다.
- **사람형 모델의 그림:** `batter-ctl.glb`는 WebP 그림 10장을 안에 담고 있고(`EXT_texture_webp` 필수) 화면이 이를 `blob:` 주소로 읽는다. 마네킹 모델에는 그림이 없다.

## 알려진 문제 (이번 넘김에서는 고치지 않았다)

아래는 우리 쪽에서 고칠 것이고 형 화면을 고쳐 달라는 뜻이 아니다(9번만 형이 정할 일이다). 형이 적은 일정으로는 11/15가 우리 수정 날이다. 고치면 해당 파일의 SHA-256이 바뀌므로 위 표도 함께 고친다. 그 전에 형이 넣는 것은 고치기 전 파일이다.

1. **탭을 가렸다가 다시 보면 화면에 있던 공의 동작이 저절로 한 번 더 재생된다.** 형 화면은 다시 보일 때 자료를 다시 확인하면서 "실제 투구" 줄을 아주 잠깐(잰 값 0.01~0.3초) "실제 투구 기록 없음"으로 바꿨다가 같은 공으로 되돌린다. 형 화면만 놓고 보면 문제가 없는 동작이다. 문제는 우리 스크립트에 있다. 되돌아온 같은 줄을 새 공으로 읽는다. 데스크톱 헤드리스 Chrome에서 다른 탭을 앞에 두었다 돌아오거나 창을 내렸다 올려서 두 판 모두 10번 중 10번 재현했고, 재확인을 맡은 다른 에이전트도 다시 재현했다. 폰에서 다른 앱에 갔다 올 때와 화면 잠금은 재지 않았다. 통신이 다시 연결될 때(online 이벤트)와 새 경기 파일이 발행될 때도 같은 일이 생겼고(흉내 낸 조건), 사람형은 공을 고르지 않은 첫 화면에서도 생겼다. health.json에 그 경기가 올라 있을 때의 동작이다(로컬 자료 기준, 공개 호스트는 확인하지 않았다). 고칠 자리는 `pz-batter.js`의 `tick()`이다.
2. **폭 359 px 이하에서 3D 상자가 넘친다.** 우타자일 때 화면이 4~5 px 넓어져 가로로 밀린다(폭 320~359에서 측정, 360 이상은 넘침 없음). 폭 320에서는 타자 그림이 존 쪽으로 들어와 타자 쪽 존 밖 표식을 가린다. 겹침이 큰 공 7개를 골라 재면 표식 하나 넓이의 20~44%가 가려졌다(선 자세 기준, 형 화면에서는 0%). 3D 캔버스가 표식보다 위에 그려지기 때문이다.
3. **색 CSS 없이 스크립트만 들어가면** 타자가 5분의 1쯤 크기로 왼쪽 끝에 그려지고(우타자일 때도 왼쪽) 실루엣이 숨는다.
4. **3D 코드가 목록 화면부터 내려받아진다.** 느린 통신망을 흉내 낸 조건(1.6 Mbps, 지연 150 ms, CPU 4배 느리게, 압축 없는 로컬 서버)에서 경기 화면이 뜨는 시간이 7.9초에서 약 16초로 늘었다(2회 측정). 다른 점검자 둘이 덜 느린 조건(9 Mbps, 지연 60 ms, CPU 4배)에서 존 행이 처음 나타나는 시간을 잰 값은 2.8초→4.9초, 1.8초→2.9~3.0초였다. 보통 조건에서는 차이가 없었다(301 ms 대 304~309 ms). 폰에서 잰 값이 아니다.
5. **결과 글이 "확인 중"인데 표식이 스트라이크나 타격이면 움직인다.** 849843 자료에는 이런 공이 없고, 만든 자료로 사람형에서만 확인했다.
6. **재생 중인 동작은 결과 없는 공으로 넘어가도 끝까지 간다**(2.9~3.1초). 이것도 만든 자료로 사람형에서만 확인했다.
7. **모델을 못 받으면 경기 화면에 들어올 때마다 3번 시도한다.** WebGL이 없는 기기에서도 모델을 먼저 요청한다.
8. **색 테마의 타격 주황(`#ffb782`)이 옅다.** 범례 점, 목록의 타격 표식, 존의 선택 고리가 흰 바탕에서 대비 1.70:1, 선택된 줄 바탕에서 1.55:1이다(형 원래 색은 12.98~14.10:1). 글자는 모두 4.5:1 이상이다.
9. **사람형 모델은 대기 중에도 조금씩 움직인다**(서 있는 동작이 계속 돈다). 마네킹은 가만히 서 있다. 조건 3을 "결과가 없으면 전혀 움직이지 않는다"로 읽으면 사람형의 대기 동작이 걸린다. 형이 정할 일이다.
10. **좌타자 화면은 우타자 화면의 거울상이 아니다.** 모델만 좌우로 뒤집고 카메라는 그대로다. 둘 다 홈플레이트를 보고 선 타자로 보이기는 한다(눈으로 본 판단).

문제 1, 3, 4는 재확인을 맡은 다른 에이전트(같은 계열 모델)가 다시 돌려 확인했다(4는 목록 화면에서 내려받는다는 사실과 느려지는 방향까지. 시간 값은 조건이 달라 서로 다르다). 2의 넘침, 7, 9는 점검자 둘 이상이 따로 쟀다. 2의 표식 가림과 5, 6, 8, 10은 점검자 한 명의 측정이다.
